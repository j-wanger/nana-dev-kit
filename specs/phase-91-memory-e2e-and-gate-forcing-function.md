# Spec: Phase 91 — Consuming-Project Memory E2E + Assumption-Gate Forcing Function

> **Post-approval discovery (DISCOVERY escape hatch, 2026-06-14):** the gate hook decision was narrowed from `--schema` + `--gate` to **`--gate` only**. Whole-file `--schema` false-blocks a *properly-gated* project when an older/prior phase block has format drift — verified on aml-substrate (passes `--gate` for its active phase, fails whole-file `--schema`). `--gate` (a phase block with ≥1 position line) catches the actual failure mode (skipping the gate); a determined agent could write a schema-valid all-accept block anyway, so `--schema` added little against gaming while risking real false-lockouts in consumers. References to `--schema` in the Approach/Constraints/Exit-Criteria below are superseded by this note.

## Objective
Bind the dev-plan assumption-approval gate with a machine-checkable forcing function so implementation cannot proceed until the gate has demonstrably fired, and repair the Memory MCP layer so it actually stores/retrieves inside consuming projects (where it is currently dead).

## Context
nana-dev-kit installs hooks, skills, templates, and an MCP memory server into `~/.claude` and into consuming projects. Two failures motivate this phase:

1. **The assumption gate keeps getting skipped.** The dev-plan Step-13 gate (maintainer takes accept/reject/don't-know positions on a plan's load-bearing assumptions, recorded as a validated `.dev-wiki/assumption-ledger.md` block) was skipped a third time this session despite a Phase-90 "fix" that was prose-only. Prose does not bind — the kit's own governing finding (checkable forcing-functions over comply-in-form prose). No enforcement artifact requires the gate to fire before implementation.

2. **Memory MCP is dead in consumers.** The server produced zero stored data across six real consuming projects while only nana-dev-kit's DB exists (94 entries). Root cause is **proven against the real `-m memory_server` launch contract**, not inferred: the server is registered with `args: ["-m", memory_server]` and Claude Code launches it with the *project* cwd (evidenced — the only DB sits at `nana-dev-kit/.memory/`, not at the configured `cwd: ~/.claude`). `python -m memory_server` resolves the package only from a cwd that *contains* it — only nana-dev-kit does (it is the kit's source repo). Verified: from a consumer cwd the real launch exits `rc=1, "No module named memory_server"`; with `PYTHONPATH=$HOME/.claude` it exits `rc=0` (clean EOF shutdown — imports resolved, server served). The venv has its `mcp` dependency (`ModuleNotFoundError: No module named 'mcp'` arises only from the *system* python3, not the venv interpreter — a red herring, ruled out). The global-pooling alternative (consumers write to `~/.claude/.memory/`) was falsified: that directory does not exist. This is **couldn't-fire, not no-demand** — which makes Phase-92's prune evidence inadmissible until repaired.

Direction confirmed via the Phase-91 assumption gate (2026-06-14): A1/A2/A3 accept, A4 (Phase-90 "recovery effective") don't-know → down-scoped out of scope. Ledger block validated (schema/gate/append-only green).

## Scope
### In scope
- A new `enforce-assumption-gate.sh` PreToolUse `Write|Edit|MultiEdit` hook (the exact matcher `enforce-spec` registers) that blocks implementation writes when the active phase's assumption-ledger block is absent or malformed, decided via `scripts/check-assumption-ledger.sh --gate` AND `--schema`.
- Single-source registration of that hook (`modules.json` → `make template` regeneration), both-landings (`~/.claude` + templates), and documentation update naming the hook as the binding mechanism behind the gate prose (`assumption-gate.md`, dev-plan `SKILL.md`).
- **Extending `scripts/register-settings.py` `cmd_mcp` to emit an `env` dict, read directly from a new `env` field in the `modules.json` mcp block** (cmd_mcp already opens modules.json for name/module — env reads there too, no new CLI argument and no install.sh call-site change; `cwd` stays CLI-passed as today, only `env` is manifest-sourced). The env carries `PYTHONPATH=$HOME/.claude` so `-m memory_server` resolves from a consumer's project cwd.
- Shipping a `.memory/` (+ `-wal`/`-shm`) gitignore entry in the template AND idempotently adding it to the six existing consumers' `.gitignore` (paths: `/Users/jwang/{aml-substrate,signal-watch,edge-screener,edge-analyst,ai-game,fate}`).
- Documenting consuming-project memory setup.

### Out of scope
- Memory server internals: embeddings/fastembed (maintainer-venv-only), dedup thresholds, consolidation, and the `source`-enum store footgun (real but orthogonal — filed separately; does not block firing).
- The Phase-92 memory keep/cut decision (this phase makes the layer *able to fire*; the prune judges demand afterward).
- Track 2 recovery measurement (B2 pilot / pre-90 baseline) — deferred per gate A4.
- Changing storage topology to global/shared, or setting `MEMORY_PROJECT_DIR` — per-project is the accepted contract (A3) and the project-cwd launch already yields it once import resolves.
- Modifying `check-assumption-ledger.sh` itself — the hook composes its existing `--gate` + `--schema` subcommands.

## Approach
Mirror the established `enforce-spec.sh` pattern for the gate hook (opt-in `.claude/enforce` OR `~/.claude/enforce` marker; `.dev-wiki` lifecycle gate; jq parse + project-relative path normalize; identical meta/test/docs allowlist; JSONL `log_firing`; fail-open on tooling absence). The gate decision runs `check-assumption-ledger.sh --schema <ledger>` (the whole file is well-formed) AND `--gate <ledger> <phase>` (the active phase has ≥1 position line) — either non-zero ⇒ exit 2 with a self-contained message, else allow. Using `--schema` alongside `--gate` closes the gap that `--gate` alone only counts `- A` lines and would pass a malformed `- A1 junk` line. Register single-source in `modules.json` with the same scope tag and the exact matcher `Write|Edit|MultiEdit` as `enforce-spec`; regenerate the settings template, never hand-edit it.

For memory, the registration writer must learn `env`: add an `env` field to the `modules.json` mcp block (value `{"PYTHONPATH": "$HOME/.claude"}` with `~`/`$HOME` expansion in cmd_mcp), and have `cmd_mcp` emit it into `mcpServers.memory` alongside command/args/cwd. Note the deliberate sourcing asymmetry: `cwd` stays CLI-passed (`--cwd`) as today; only `env` is read from the manifest inside cmd_mcp — both land in the same dict. The existing merge already *replaces* the whole `mcpServers.memory` dict (`data["mcpServers"][name] = {...}`), so no stale-key ghost survives — but it discards any prior `env`, so the env must be written every regeneration. `MEMORY_PROJECT_DIR` is deliberately NOT set; with import resolved and project-cwd launch, `project_db_path` already resolves to `<project>/.memory/memory.db`, auto-created on first store/search.

### Domain Research Questions

This affects whether the new-phase double-block (enforce-spec + enforce-assumption-gate) shows the agent the gate's message; assume only-first-surfaces and make each message self-contained so sequential discovery still resolves cleanly.
- Does any consuming project carry a `.claude/enforce` marker, or do they all rely on the global `~/.claude/enforce`? (Determines where the gate is armed.)

## Constraints (CRITICAL)
- **The gate enforces that the gate FIRED, not that reasoning was good** — a deterministic hook cannot judge quality, and `all-accept` remains allowed-but-warned. Guard: the hook requires a `--schema`-valid ledger whose active-phase block has ≥1 position line (`--gate`); state plainly in docs that this stops *skipping* and *malformed/empty* blocks, not rubber-stamping. Prevents implying the hook closes a gap it cannot.
- **The gate must not be satisfiable by an empty or absent block** — `--gate` requires a phase block with ≥1 `- A` line (positions were taken). Guard: the firing test includes a `touch`ed-empty-ledger negative control (BLOCKS) and a no-block-for-active-phase control (BLOCKS). *Post-approval (`--gate`-only):* whole-file `--schema` was dropped — a malformed *current*-phase block is the accepted gaming-vs-false-lockout tradeoff (a determined agent could write a schema-valid all-accept block anyway; `--schema` false-blocked properly-gated consumer ledgers with format-drifted *prior* blocks). The test instead asserts a malformed *prior* block does NOT false-block a gated current phase.
- **The new-phase window (spec exists, gate not yet run) must block with a CLEAR message** — this double-block with `enforce-spec` is *correct* (you must gate before implementing). Guard: stderr names exactly what is missing and the remedy ("run the dev-plan Step-13 gate / append the ledger block"); because stderr may be masked if enforce-spec fires first (DRQ-1), the message must stand alone so fixing the spec then re-hitting the gate is self-explanatory.
- **The MCP env change must reach BOTH the template and the live settings, with no half-applied state** — `register-settings.py` is the single source; hand-editing settings.json is forbidden and the template is generated. Guard: after the cmd_mcp change, regenerate and read-back assert the `env.PYTHONPATH` value equals the expanded `$HOME/.claude` (not merely that a `memory` key exists) in BOTH templates/.claude/settings.json and `~/.claude/settings.json`. Prevents a code change that compiles but never emits the env.
- **Activating per-project memory must not commit a binary DB or memory contents** — six existing consumers have their own `.gitignore` that the template won't update. Guard: idempotently append `.memory/` to each consuming project's `.gitignore`; the template ships it for new projects. Prevents a binary SQLite (possibly with sensitive context) being checked in on first commit.
- **Acceptance cannot be proven inside the kit repo** — the memory server already works in nana-dev-kit, and clean-context behavior is unmeasurable in-kit (Ph80). Guard: the memory exit criterion exercises the real `-m memory_server` launch from a NON-package-bearing cwd (a mktemp dir or a consumer), not the kit repo.

## Success Vision
Implementation writes are refused — with an actionable message — in any phase whose assumption gate has not fired (or whose ledger block is malformed), in a project where enforcement is armed; and the refusal clears the moment a valid ledger block exists. A maintainer working in a consuming project can store a memory and retrieve it in a later session, with the DB living beside that project and never entering version control. The assumption-gate prose now points at a real hook, so occurrence #4 cannot happen silently. Both changes ship through the single-source registration path with no ghosts and no drift, verified by firing real events and the real server launch rather than checking for file presence.

## Assumptions
- The gate arms via the global `~/.claude/enforce` marker (present), which covers nana-dev-kit (no project-local marker) and every project. If false (the global marker is removed or a target consumer is unarmed): the gate is silently disabled there — record which projects are armed and surface it; arming is a setup precondition, not a code bug.
- `check-assumption-ledger.sh --gate <ledger> <phase>` returns non-zero iff the active phase has no positions block, and `--schema` returns non-zero on any malformed `- A` line. If false (either passes on a bad block): strengthen the checker before relying on it as the gate decision.
- The active-phase number and the ledger block header stay in sync across renumbering (the kit renumbers phases routinely, 90→91→92). If false: the gate keys on a number whose block was renamed and false-blocks a gated phase — match on the active phase number written to active-phase.md and renumber both together.
- Claude Code launches the MCP server with the *project* cwd (proven: the only DB sits at the project path, and the real `-m` launch fails from a consumer cwd without PYTHONPATH). If false (it honors the configured `cwd: ~/.claude`): the server would resolve everywhere and the root cause is wrong — the no-PYTHONPATH negative control in the real-launch exit criterion is the falsifier; STOP and re-diagnose if it unexpectedly passes.
- `cmd_mcp` writes a full-dict replacement for `mcpServers.memory` (confirmed: `data["mcpServers"][name] = {...}`), so adding `env` cannot collide with a stale partial entry — but the env is re-emitted every regeneration since the prior dict is discarded. If false (the writer is later changed to a partial merge): re-verify no stale `env`/`cwd` survives.
