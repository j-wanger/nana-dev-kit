# Spec: Phase 102 — Pillar 2: contract-driven downstream-worker loop

## Objective

Build and measure a **contract-driven iteration loop**: a downstream worker (`opencode`) implements a delegated edge-screener task, the contract's deterministic **visible guardrails** score it, and on failure the worker gets **rich feedback** (the failing assertion + a counterexample) and retries — up to a capped budget. Measure whether the loop (a) **recovers the single-shot floors** Phase 101 found *via feedback, not just resampling*, and (b) produces **truthful** work vs **games** the visible guardrails (passes them but fails a **held-out** validation it never sees).

## Context

The rung-C culmination. Phase 100 ([[contract-fidelity-screen]]): contracts add no fidelity on easy tasks (amplifier-null). Phase 101 ([[harder-corpus-screen]]): on hard integrity tasks where bare fails, naming the invariant helps *task-specifically* — but the **decision-lag floored even with the invariant named** (the worker understood "weights decided at k first earn return k+1" but couldn't implement the subtle `pending` deferral in one shot — implementation difficulty, not feedback-starvation). This phase asks the full rung-C thesis: does wrapping the worker in a **loop governed by the contract** recover that floor — *and is any recovery from the feedback or merely from more attempts?* — and does iteration breed **gaming** (iterate-to-green on the visible checks while failing a deeper validation)? It connects pillar 1 (the check, `scripts/check-fidelity.py`), pillar 3 (the dashboard), pillar 2 (the loop).

Direction gate (2026-06-22, ledger Phase-102, all_accept:true): A1 **rich feedback**; A2 **visible-guardrail loop + held-out validation** (gaming = loop-pass but held-out-fail); A3 arms **single-shot / contract-loop / bare-loop** — *extended here with a best-of-N resampling control per the adversarial review*; A4 **opencode loop** (`run --continue`). Reuses the Phase-100/101 harness.

## Scope

### In scope
- A gitignored apparatus `companion/research/contract-loop/`: a per-(task,arm,run) **loop runner** (opencode implements in a per-run edge-screener copy → score the contract's visible guardrails via `check-fidelity.py` → on fail, feed back the failing assertion + a counterexample → `opencode run --continue` → ≤ budget iterations → then run the **held-out** validation once), a byte-frozen pre-registration, results, a verdict.
- The **visible/held-out split** per task (keystone, reused from Ph100/101): the loop gate = a specific-example / functional visible guardrail set; the held-out validation = the generative rigorous integrity test (e.g. `test_f2` perturbation) the worker never sees.
- **4 arms**: **single-shot** (1 attempt, Ph101 baseline) / **best-of-N** (N *independent* attempts, NO feedback, take the best — the resampling control) / **contract-loop** (N iterations WITH feedback against functional + named-invariant visible guardrails) / **bare-loop** (N iterations with feedback against functional guardrails ONLY, no named invariant).
- A mechanical **verdict**: floor-recovery rate, *feedback lift (contract-loop − best-of-N)*, iterations-to-converge, terminal-failure buckets, gaming rate — per arm, with intervals.

## Approach

For each (task, arm, run): a per-run edge-screener copy (target function stubbed, held-out test absent). **single-shot** = one opencode attempt. **best-of-N** = N independent fresh opencode attempts (no feedback) — take the one with the best visible-guardrail score. **contract-loop / bare-loop** = opencode implements → the contract's *visible* guardrails (`check-fidelity.py`) score it → if any fail, build rich feedback from the *visible* guardrail's failure (assertion + counterexample) and continue the opencode session → stop on visible-pass or the iteration cap. After every arm's terminal impl, run the **held-out** generative validation once, in a stage the worker's session never touched. The feedback-vs-resampling decomposition (contract-loop vs best-of-N) is the crux; the bare-loop isolates the invariant's value within the loop. Read the frozen decision rule mechanically.

### Domain Research Questions
- Per task, is there a *visible* guardrail SEPARABLE from the held-out generative test — a hand-writable impl that passes ALL visible checks yet FAILS held-out (so gaming is detectable in principle)? If none can exist, the held-out is redundant and measures nothing.
- What feedback granularity drives convergence on an implementation-difficulty floor — raw assertion, minimal counterexample, structural hint — without crossing into the answer (the held-out test or a reference patch)? And does the counterexample handed back become a memorize-able attack surface (held-out must use DIFFERENT inputs)?
- How is opencode `--continue`/`--session` made a real bounded retry (the worker builds on its prior attempt; context doesn't bloat into a blind restart)?

## Constraints (CRITICAL)

- **Feedback ≠ resampling (the best-of-N control)** — the loop's recovery over single-shot is confounded with simply taking more attempts. Guard: a best-of-N arm (N independent single-shot samples, no feedback) runs at the SAME N as the loop's cap; the headline feedback claim is `contract-loop − best-of-N`, not `contract-loop − single-shot`. If best-of-N matches the loop, the gain is resampling, not feedback — reported as such. **Best-of-N terminal selection is pinned in the freeze (no post-hoc analyst choice of which visible-passer gets held-out-scored): the first sample by attempt order to reach full visible-pass, else the highest visible-pass-count (ties → first); that impl's held-out is the one scored.**
- **Pinned effect floor (no tiny-n over-read)** — `≥1 task × 4 arms × n≥3` makes per-arm rates coarse; a 2/3-vs-1/3 split must not be upgraded to "feedback recovers the floor." Guard: the frozen decision rule pins a minimum separation (non-overlapping per-arm intervals OR delta ≥ k·spread, k frozen) below which `verdict.md` reads **"directional / underpowered, routed forward,"** never a recovery/lift headline (mirrors the Phase-100 effect-floor).
- **Visible loop-gate ≠ held-out validation, detectable in principle** — if iterating against the validation, gaming is invisible. Guard: before scored runs, a seeded impl that passes ALL visible checks and FAILS the held-out MUST exist per task (the gaming-detectable-in-principle control); a task with no such impl has a redundant held-out and is rejected.
- **Held-out never leaks into the worker's session (hard boundary)** — leaking it trains the worker on the answer; "no gaming" becomes a measurement artifact. Guard: the held-out runs in a separate stage/file-tree the worker never touches and that the visible checks never import (transitive-reachability checked); a freeze-time + per-run grep of the ENTIRE feedback transcript AND the shared prompt/session for held-out test names / paths / expected-value literals → any hit VOIDS the run. (The grep runs on the single-shot + best-of-N arms too, since all arms share the prompt by the parity constraint — an accidental held-out reference in the shared prompt voids all arms.)
- **Controls-first gaming-detector + alive visible checks** ([[HEU-012]]) — a seeded GAMING impl MUST be caught by the held-out (visible-pass + held-out-FAIL); a seeded HONORED impl passes both; AND every visible check must FAIL on ≥1 seeded-defect fixture (red-on-broken). Recorded before scored runs; a held-out that passes its seeded gamer, or a visible check that catches no seeded defect, is rejected; all-dead → abort.
- **The worker cannot edit or weaken the scoring** — gaming via deleting/weakening a check, editing the test file, or hardcoding the fed-back counterexample's expected output. Guard: visible checks + the held-out are scored EXTERNALLY (the worker's editable surface is the target function only); the fed-back counterexample's inputs differ from the held-out's, so memorizing it does not pass held-out; the scoring copy is rebuilt from the frozen contract each iteration.
- **Terminal-failure is bucketed, not one bit** — budget-exhaustion conflates "converging but truncated" with "stalled" with "regressing." Guard: record per-iteration the visible-pass-count delta; classify a non-converged run as converging-truncated (monotone up, hit cap) / stalled (no delta ≥2 iters) / regressing (delta down). Pre-registered buckets.
- **Iteration is a real retry; non-convergence is a floor not infra** — Guard: `--continue`/`--session` so each iteration builds on the prior impl+feedback (a fresh-every-iteration fallback is explicitly the best-of-N control, NOT the contract-loop); an opencode error / no-edit / empty-diff / early "done" with visible-fail = infra-fail (excluded, re-rolled) vs ran-but-never-passed = floor (scored). Outcome-blind infra predicate.
- **Information parity — arms differ in EXACTLY one variable** — Guard: bare-loop vs contract-loop configs are byte-identical except the single invariant-naming line (a recorded diff asserts exactly that); single-shot/best-of-N/contract-loop share the same prompt + functional guardrails + feedback template + cap, differing only in iteration count + feedback presence.
- **Deterministic visible checks** — a flaky check makes feedback noise and burns budget on phantom failures. Guard: visible guardrails carry no timestamp/ordering/RNG/wall-clock dependence (reuse Ph100 check-determinism); a check re-run on the same impl yields the same verdict.
- **Frozen before scored runs (anti-retrofit)** — corpus + visible/held-out split + 4 arm configs + feedback template + iteration cap + N + best-of-N selection/tie-break + the decision rule (incl. the pinned effect floor) byte-frozen (sha256 `.frozen`) BEFORE any scored loop; controls + the single-shot-floor-still-exists check precede the freeze. Guard: `shasum -c .frozen` after; no re-pick / feedback-enrich / cap-change / arm-add after results.
- **The real edge-screener is never mutated** — per-run copies; src checksum identical before/after; `git -C /Users/jwang/edge-screener status` clean on src/tests.
- **Ships nothing; apparatus gitignored; claim scoped + worker pinned** — no kit code change; `companion/research/contract-loop/` never committed; the verdict bounds the claim to these tasks, this held-out probe, this feedback design, and `opencode/big-pickle`; n + cap + effect-size pinned in the freeze; rates reported with intervals.

## Success Vision

An honest, *decomposed* answer to the rung-C question: on a task a worker fails single-shot for implementation-difficulty reasons, does contract-driven **feedback** (beyond mere resampling) drive it to a *genuinely correct* result, or to one that **games** the visible checks? Excellence is a verdict made trustworthy by the best-of-N resampling control (feedback isolated from luck), a proven gaming-detector (held-out catches a seeded gamer), feedback that never leaks the held-out (transcript-grep clean), a bare-loop control (the invariant's value within the loop), a re-verified single-shot floor, and the frozen rule — read mechanically with intervals, whichever way it falls. A clean **"feedback recovers the floor beyond best-of-N and the held-out confirms it's real"** is a strong rung-C positive; **"the loop reaches visible-green only by gaming"** is an equally valuable warning; **"recovery is just resampling (best-of-N matches the loop)"** or **"even rich feedback doesn't recover the floor"** both sharply bound where contract-governed delegation helps. What excellence is NOT: recovery from visible-green alone, recovery confounded with resampling, gaming from a leaked held-out, or an iteration that was a blind restart.

## Checkpoints

- After the visible/held-out split + seeded gaming/honored impls are built and the held-out catches the gamer + passes the honored, AND each visible check fails a seeded defect (per task): report — the gaming-detector and the visible checks are alive before any loop.
- After re-verifying the single-shot floor still exists on decision-lag: if it no longer floors (the worker now aces it single-shot), STOP and report there is no floor to recover (the model improved / the task is too easy now).
- After a single pilot loop on decision-lag (one arm, one run): confirm iterations are real retries (each builds on the prior + feedback), the feedback transcript carries no held-out leak, the worker cannot edit the checks, and the edge-screener src is unmutated — before the full n.
- After the pilot, BEFORE freezing: confirm ≥1 task has a separable visible/held-out split (a seeded gamer passes visible / fails held-out). If none separable → STOP and record that gaming cannot be measured for this corpus (floor-recovery only, or the informative null).
- If opencode `--continue` cannot iterate usefully (context bloat / blind restart) or the held-out cannot be separated: STOP and re-scope rather than ship a blind-restart or iterate-to-green-undetectable screen.

## Assumptions

- The decision-lag single-shot floor still reproduces. If false (the worker now aces it single-shot): no floor to recover — report it and re-scope (find a harder task or measure gaming only).
- opencode `--continue`/`--session` iterates with accumulating context. If false: fall back to fresh runs with the accumulated impl+feedback in the prompt, recording the substrate change — and the verdict MUST down-grade the claim from "true session-continuation iteration" to "feedback-in-prompt iteration (not session-continuation)" (the fallback partially realizes the blind-restart failure mode, so the "true iteration" excellence claim is voided, not merely footnoted).
- A separable visible/held-out split exists (a seeded gamer passes visible / fails held-out) for ≥1 task. If false: that task can't measure gaming → floor-recovery only; if NO task is separable, report the limitation.
- Rich feedback is constructible from the visible guardrails without leaking the held-out (counterexample inputs disjoint from held-out inputs). If false (the only informative feedback IS the held-out): the gaming question can't be cleanly measured — report and restrict to floor-recovery.
- 4 arms × cap(~5) × n≥3 × the small corpus is affordable in opencode time/cost. If false: drop n or a task before dropping the best-of-N control or the bare-loop; scope the claim to the reduced power and report intervals.
- The finding is worker-conditional. If a stronger/weaker worker would change it: bound the claim to `opencode/big-pickle` and this held-out probe (do not generalize to "loops work / don't work").
