# Spec: Hook Consolidation and Enforcement Activation

## Objective

Make a project's enforcement hooks fully functional from its own per-project scaffold, independent of fragile global `~/.claude` state, by reconciling the three disagreeing hook-registration sources into a single scope-tagged source of truth in `modules.json`, generating the per-project template from it, and making the enforce opt-in marker project-reachable. Verify enforce-spec *actually fires* (exit 2) in a freshly-scaffolded project — not merely that the hook file exists.

## Context

The Phase 54-56 C/D stock-screener experiment scored well on engineering but the cognitive/enforcement layer contributed nothing. Root cause for enforcement: it never fired. enforce-spec was registered only in global `~/.claude/settings.json`; the test's backup/restore cycle wiped global state and enforcement silently vanished. This is the third instance of the cascade-failure anti-pattern (MCP CWD, pre-compact orphan, nana-init marker).

Audit of the current tree confirms three registration sources that disagree:
- `templates/.claude/settings.json` — hand-maintained, 9 hooks, **no enforcement hooks**. Used by py-init/ts-init via `cp -r`.
- `modules.json` `project_local.hooks` — 7 hooks, drifted from the template by `post-commit.sh` + `pre-compact.sh`. Used by `install.sh --project-local`.
- `modules.json` `dev-wiki` module `hooks` — 11 hooks including all enforcement. Registered into global `~/.claude/settings.json` by `install.sh`.

A fourth, undocumented activation axis surfaced during investigation: the enforce opt-in **marker is global** (`$HOME/.claude/enforce`), checked by all three enforce hooks (enforce-spec/memory/loop). So per-project hook *registration* alone is insufficient — a fresh scaffold would register enforce-spec but it would still fail-open because the marker lives in global `~/.claude`. Both axes (registration AND marker) must be made project-reachable for a scaffold to enforce on its own.

`scripts/register-settings.py` already writes a settings.json from a hook list; it does NOT generate the template (the template is hand-maintained — the drift source). The template can be generated by extending the existing script, requiring no new machinery beyond scope-aware filtering.

This phase is Fix 1 of a 5-fix roadmap (handover Phase 57+). Fixes 2-5 (domain research in dev-plan, AGENTS.md reshape, actionable cognitive readiness, nana-init discoverability) are separate later phases per "one fix, one verification, one debrief."

## Scope

### In scope
- `modules.json`: replace the three hook lists with one canonical scope-tagged `hooks` array (each entry: `scope: "project" | "global"`). Preserve `markers`, `extra_dirs`, `ghost_cleanup`.
- `scripts/register-settings.py`: filter the canonical list by `--scope`; add a regeneration mode that writes a clean template from scratch.
- `templates/.claude/settings.json`: regenerated as a build artifact from `modules.json` (now includes all 17 project-scoped hooks).
- `Makefile`: a `template` target that regenerates the template.
- Drift test: regenerate-to-temp and diff the committed template (deterministic anti-drift validator).
- Marker model: enforce-spec/memory/loop accept a project-local marker (`.claude/enforce` for spec+loop, `.claude/enforce-memory` for memory) OR the global marker (backward-compatible OR logic). Ship the spec/loop marker (`.claude/enforce`) in the template and create it on `install.sh --project-local`, making spec+loop enforcement self-sufficient by default. **enforce-memory stays OPT-IN** — its marker is deliberately NOT shipped: it gates on `.claude/.memory-consulted` and requires a working memory MCP, which a bare scaffold does not configure (the template carries no `mcpServers`). Shipping it on-by-default would block every write in a memory-less scaffold with no way to satisfy the gate. enforce-memory is still *registered* so a user can enable it per-project with `touch .claude/enforce-memory`.
- Headline verification test: a project scaffolded from the template, under minimal firing conditions, makes enforce-spec exit 2.

### Out of scope
- Flipping the kit repo itself to per-project self-enforcement (committing a live `.claude/settings.json` + marker). Self-lockout risk mid-phase; the kit already enforces via existing global wiring. Deliberate later step.
- Fixes 2-5 (domain research, AGENTS.md, cognitive readiness, nana-init).
- Removing pre-existing enforcement hooks from any user's global `~/.claude/settings.json` (upsert-only; no destructive migration).
- New hook event types or new enforcement logic. This phase moves WHERE hooks register and HOW the opt-in marker is found — not WHAT they check.
- Heuristic capture (HEU "mandatory over advisory") — belongs to a later debrief/phase, not Fix 1.

## Approach

Single source of truth, then generate, then verify firing.

1. **Canonical scope-tagged hook list in `modules.json`.** One top-level `hooks` array; each entry `{event, matcher, script, type?, scope}`. Scope rule: *project if it reads/writes project state (.dev-wiki, specs, .claude/enforce, .nana, project files); global if it is session/user ergonomics independent of the project.* This yields 17 `project` hooks and 1 `global` (context-size-check). Per-module `hooks` and `project_local.hooks` are removed; `project_local.extra_dirs` and module `markers`/`ghost_cleanup` are preserved.
2. **Scope-aware `register-settings.py`.** `cmd_hooks` reads the canonical list and filters by `--scope` (global → scope==global; project-local → scope==project). A regeneration mode (e.g. `--regenerate`) builds the hooks block from scratch so the generated template is deterministic and not a merge into stale content.
3. **Generated template + drift test.** `make template` regenerates `templates/.claude/settings.json` from `modules.json`. A test regenerates to a temp file and diffs the committed template — drift fails the suite.
4. **Project-reachable marker.** enforce-spec/memory/loop allow when EITHER `.claude/enforce`(`-memory`) (project) OR `$HOME/.claude/enforce`(`-memory`) (global) is present. An empty marker file ships in the template so `cp -r` distributes it; `install.sh --project-local` also creates it.
5. **Firing verification.** A test scaffolds from the template into a temp dir, sets minimal firing conditions (`.dev-wiki/`, `.claude/rules/active-phase.md` naming a phase with no spec and no `[x] spec` gate, project marker present), pipes a no-spec Write event through `.claude/hooks/enforce-spec.sh`, and asserts exit 2 — in an empty HOME, proving no dependency on global state.

## Domain Research Questions
1. Does Claude Code double-fire a hook registered in BOTH global `~/.claude/settings.json` and a project `.claude/settings.json`? Assessment: enforcement hooks are idempotent gates (exit 0/2 deterministically) and dev-wiki hooks are advisory/fail-open, so double-fire is at worst cosmetic (e.g. duplicated session-start banner). The full single-source model (enforcement = scope project only) avoids the case entirely for fresh installs; pre-existing global registrations remain by upsert but are harmless.
2. What is the minimal set of conditions under which enforce-spec reaches its `exit 2` path? (marker present, `.dev-wiki/` exists, file path not allowlisted, no `[x] spec` gate, no valid `specs/<slug>.md`). The firing test must construct exactly these.
3. Should the shipped marker be created by py-init (any scaffold) or only by dev-init (lifecycle adoption)? The marker is inert without `.dev-wiki/` (hooks fail-open), so shipping it in the template is harmless and makes a single `cp -r` self-sufficient; dev-init coupling would leave py-init-only scaffolds dormant.

## Constraints (CRITICAL)

- **Backward compatibility — no destructive global migration.** Existing `~/.claude/settings.json` enforcement registrations and the global `~/.claude/enforce` marker must keep working. Marker logic is additive (project OR global). Guard: enforce-spec with only the global marker (no project marker) still reaches its enforcement path — existing kit behavior unchanged.
- **No self-lockout.** All gate-relevant artifacts (spec, active-phase.md) are written before any edit to non-allowlisted files (`modules.json`, `scripts/`, `install.sh`, `Makefile`). The kit's live enforce-spec must continue to allow this phase's own edits via the present valid spec. Guard: a valid `specs/phase-57-*.md` with provenance marker exists before implementation edits.
- **Single source of truth.** After this phase, exactly one list in `modules.json` defines hook registration; the template is generated, never hand-edited. Guard: drift test (regenerate == committed) is part of `make test`.
- **Fail-open preserved.** The marker change must not turn any fail-open hook into a blocking hook in a context where it previously fail-opened (no `.dev-wiki/`, no marker, missing jq). Guard: enforce-spec with neither marker present still exits 0.
- **Verify firing, not presence.** The phase is not complete on "enforce-spec.sh exists in the template." It is complete when a scaffold-from-template makes enforce-spec exit 2 under firing conditions. Guard: the headline test asserts exit code 2, not file existence.

## Success Vision

A developer scaffolds a project from the template (or `install.sh --project-local`) and gets a self-enforcing harness by default: enforce-spec and enforce-loop fire from the project itself (hooks registered + `.claude/enforce` marker shipped), independent of global `~/.claude` state. enforce-memory and the dev-wiki lifecycle hooks are registered too; enforce-memory fires once opted in (`touch .claude/enforce-memory`), kept opt-in because it depends on a memory MCP a bare scaffold lacks. Resetting, restoring, or never having a global `~/.claude` install does not silently disable spec/loop enforcement. `modules.json` is the one place hooks are declared; the template is regenerated by `make template` and a test makes drift impossible to commit unnoticed. The "looks registered vs actually fires" gap is closed by a test that pipes a real event through the hook and checks the block, so the failure that survived two experiment runs cannot recur unobserved.

## Exit Criteria (machine-checkable)

- [ ] `jq -e '(.hooks|length)>0 and (.hooks|all(.scope=="project" or .scope=="global"))' modules.json` (canonical scope-tagged hook list exists; every entry tagged)
- [ ] `grep -q 'enforce-spec.sh' templates/.claude/settings.json && grep -q 'enforce-loop.sh' templates/.claude/settings.json && grep -q 'enforce-memory.sh' templates/.claude/settings.json` (generated template registers the enforcement hooks)
- [ ] `make template && git diff --quiet -- templates/.claude/settings.json` (template is a deterministic generated artifact, in sync with modules.json)
- [ ] `grep -q '\.claude/enforce' templates/.claude/hooks/enforce-spec.sh && test -f templates/.claude/enforce` (enforce-spec honors a project-local marker; marker shipped in template)
- [ ] `bash tests/test_settings_template.sh` (headline firing test: scaffold-from-template + minimal conditions makes enforce-spec exit 2)
- [ ] `make test` (full suite green, no regressions)

## Checkpoints

- After Task 1 (modules.json restructure): report the scope assignment (which hooks are project vs global) before regenerating anything.
- After Task 3 (template generated + drift test): confirm the generated template diffs cleanly and enforcement hooks are present before touching marker logic.
- After Task 5 (firing test): confirm enforce-spec exits 2 in an empty HOME with only the project marker — proving the scaffold is self-sufficient. If it only fires with the global marker present, the marker fix is incomplete — STOP and fix before declaring done.
- If Claude Code is observed to double-fire registered hooks harmfully (not just cosmetically): STOP and reconsider whether enforcement should be scope project-only with kit migration brought forward.

## Assumptions

- `register-settings.py`'s `upsert_hook` produces a deterministic settings.json given a fixed hook list and order (required for the drift test). If false: sort/normalize before diff, or snapshot a canonical form.
- Claude Code merges global + project `settings.json` hooks rather than one overriding the other. If false (project overrides global): the kit would lose global enforcement once it gains a local settings.json — but the kit is out of scope this phase, so no immediate impact; note for the kit-adoption step.
- The enforce-spec slug derivation (`active-phase.md` "Phase:" line → `specs/phase-N-<slug>.md`) is unchanged by this phase. The phase name avoids special characters so the slug is clean (`hook-consolidation-and-enforcement-activation`).
- Shipping an empty `.claude/enforce` marker in scaffolds is acceptable default-on behavior for enforcement (inert until `.dev-wiki/` exists). If the user wants opt-out-by-default instead, the marker is shipped but enforcement still requires `.dev-wiki/`, so the blast radius is limited to dev-wiki projects.
