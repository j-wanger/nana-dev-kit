The rung-C culmination: a downstream worker (opencode) executes a delegated edge-screener task in a LOOP governed by the contract — implement → score against the contract's deterministic guardrails → feed the failing guardrail back → retry → until pass or an iteration budget. Measure whether the loop (a) RECOVERS the single-shot floors Phase 101 found (decision-lag: the worker couldn't implement the subtle pending-lag in one shot even when told the invariant) and (b) produces TRUTHFUL work vs GAMING the guardrails over iterations (passes the loop but fails a HELD-OUT validation it never sees). Connects all three pillars: the check (1) + the dashboard (3) + the loop (2).

RecommendationRecommend a contract-driven loop where the worker iterates against the contract's VISIBLE guardrails (NOT the held-out integrity test), with RICH feedback (the failing guardrail's assertion error / counterexample — not just pass/fail), and a SEPARATE held-out validation run at the end to detect gaming. Arms: single-shot (Ph101 baseline) vs contract-loop vs bare-loop (loop on functional tests only, no named invariant) — to isolate the loop's value from the contract's. Focus on decision-lag (the floor) + ≥1 other in-band task. The crux is feedback richness: pass/fail alone likely won't recover the subtle floor; the assertion error / counterexample likely will.
