- [scope:mcpServers settings.json registration] The settings.json mcpServers registration must actually be read and honored by the running agent at the path/scope the plan registers it under — cost-of-error: HIGHEST. If the agent reads a different settings file (project vs global), or ignores the cwd/launch directory the plan assumes, the server is registered-but-never-launched and the entire feature is silently dead (no error, just no memory). Is it actually so: is the registration in the file the agent loads, and does the agent honor it?
- [scope:memory persistence store/path] The memory store must persist writes to disk at the exact path the next session reads from — cost-of-error: HIGHEST, this IS the success criterion. If session N writes to one DB location and session N+1's server launches with a different cwd/path (in-memory, /tmp, per-session dir, or a package-dir vs parent-dir mismatch), a recorded decision is silently unrecoverable next session. The plan's success test ('recall in the next session') passes ONLY if path is stable and identical across launches. Is it actually so: does the store persist, at one canonical path, across process restarts?
- [scope:python -m memory_server launch] The `python -m memory_server` command must resolve and start cleanly in the agent's launch environment — cost-of-error: HIGH. If the module isn't importable (not installed / wrong interpreter / wrong PYTHONPATH / wrong cwd), the MCP server fails to start and memory_store/memory_search never register as callable tools. The plan assumes `python` (not python3/venv) resolves to an interpreter that can import memory_server. Is it actually so: is the package installed in the interpreter `python` points to, and is the working directory correct for module resolution?
- [scope:memory_store / memory_search tool surface] The memory_store and memory_search MCP tools must be exposed by the server, callable from a normal session, and behaviorally correct (store actually writes; search actually retrieves the stored item) — cost-of-error: HIGH. A registered server that exposes the tools but where search can't find what store wrote (tokenization, dedup, indexing, or query-mismatch failures) fails the success criterion even though every wiring step 'succeeded'. Is it actually so: round-trip write-then-read returns the decision, not just an empty/zero result?
- [scope:cross-session recall mechanism] The agent must actually CALL memory_search at the start of (or during) the next session — cost-of-error: HIGH. The plumbing can be perfect, yet 'recall' never happens if nothing prompts the agent to query memory in session N+1. Storing is voluntary and recall is voluntary; without an activation point (hook/instruction), the success test only passes when a human manually asks the agent to search. Is it actually so: is there a forcing mechanism, or does recall depend on the agent spontaneously choosing to query?
- [scope:agent voluntary store behavior] The agent must reliably decide WHAT to store and DO so during session N — cost-of-error: MEDIUM-HIGH. If the agent doesn't recognize a 'decision' worth recording, or skips the store call, there is nothing to recall regardless of correct plumbing. The plan assumes store is invoked at the right moments without specifying the trigger.
- [scope:MCP runtime / Claude Code MCP support] The host runtime must support stdio MCP servers, spawn the configured server process, and keep it alive for the session — cost-of-error: MEDIUM-HIGH. Assumed-already-works infrastructure the plan never verifies: if MCP support is disabled, the schema format is wrong, or the process is killed/not respawned, tools are unavailable. Is it actually so: does the host launch and maintain the server process per session?
- [scope:settings.json schema validity] The mcpServers entry must conform to the host's expected JSON schema (correct keys, command/args shape) and not corrupt the rest of settings.json — cost-of-error: MEDIUM. A malformed merge can break server launch or, worse, invalidate other settings (other hooks/permissions). Is it actually so: is the entry schema-valid and the file still parseable after edit?
- [scope:dependencies (sqlite/embeddings)] Any storage/search dependencies the server needs (e.g. sqlite, optional embedding providers) must be present and functional — cost-of-error: MEDIUM. Missing deps could degrade search to a fallback path or fail writes; the plan treats the server as a black box that 'just works'. Is it actually so: are storage and search backends available in the launch env?
- [scope:scope/isolation of stored memory] Stored decisions must be retrievable from the SAME logical scope (project vs global) the next session runs in — cost-of-error: MEDIUM. If store writes to project scope but next session searches global scope (or a different project root), recall returns nothing despite correct persistence. Is it actually so: do write-scope and read-scope match across the two sessions?
- [framing] Cross-session decision recall via this memory layer is worth solving AT ALL given the agent already loads decisions from .claude/rules, dev-wiki, and code/tests — cost-of-error: HIGH on wasted effort. Prior measurement in this very kit (Ph70/71/77/78 amplifier program) found re-presenting decisions is NULL-value: every decision was recoverable from artifacts the model already has. The plan assumes the recall problem exists; the existing evidence suggests the headroom may be zero, making the whole feature low-yield.
- [framing] An MCP memory server is the RIGHT substrate for persistence — cost-of-error: HIGH. The plan assumes a live server process over simpler alternatives (a checked-in decisions file, dev-wiki articles, working-knowledge.md). A subtraction-test challenge: a flat file the agent reads at session start is deterministic, has no launch/CWD/process-liveness failure modes, and may achieve the same recall with far less plumbing. Is the running server earning its complexity?
- [framing] The 'recall in next session' success criterion as stated will actually demonstrate cross-session memory rather than confounded behavior — cost-of-error: MEDIUM. A single one-shot success could be the agent re-deriving the decision from context/code rather than from the store, or a manual-prompt artifact; the measured effect needs to replicate (n>1, decision genuinely NOT recoverable from other loaded context) to count as a real, banked effect rather than a noise draw.
