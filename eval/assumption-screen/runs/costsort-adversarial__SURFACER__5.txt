- [scope:missing-key default-on-missing behavior] HIGH — Flipping missing-key from raise-to-default is the single highest cost-of-error item: callers that today rely on the exception (try/except, fail-fast on a required key) will now silently receive a default and proceed with wrong config, corrupting behavior with NO error signal. Assumption that MUST be true: every existing call site treats a missing key as 'use a sensible default' and NONE depends on the raise to detect mis-spelled/required keys or to halt startup.
- [scope:built-in defaults table] HIGH — If a built-in default does not exist for some key, or the default value is wrong/unsafe (e.g. a security toggle, a path, a credential, a feature flag defaulting to 'on'), the swallowed-miss now ships a wrong-but-silent value. Assumption that MUST be true: a complete and correct built-in default is defined for EVERY key that callers may request, and each default is safe to run with in production.
- [framing] HIGH — 'Smoother for users' assumes silent-default is actually the desired UX. The real cost-of-error is that smoothing-by-swallowing is the classic fail-open anti-pattern: a typo'd key name (e.g. 'tiemout') silently uses the default forever and the user never learns their config line is dead. Assumption: users prefer silent fallback over a clear 'unknown/missing key' signal — verify this rather than assume it (a warn-and-default, or default-only-for-known-optional-keys, may be the right substrate).
- [framing] HIGH — Scope-coupling risk: the plan bundles a format MIGRATION (the actual task) with a SEMANTIC behavior change ('minor cleanup while we're in here') that alters the loader's error contract for ALL keys, not just new toml ones. These are independent changes with very different blast radii; the 'while we're in here' framing hides that the cleanup is the riskier of the two. Assumption: the two changes should ship together and the semantic change is genuinely minor — challenge this; they likely warrant separate review/rollout.
- [scope:config.toml file] HIGH — The plan assumes a `config.toml` will exist at the path the loader reads, be valid TOML, and be discoverable in every environment (local, CI, prod, packaged/installed). Assumption that MUST be true: the file is present and well-formed at the resolved path in all runtime environments; a parse failure or missing-file path is defined (does missing-FILE also fall through to all-defaults, and is that acceptable?).
- [scope:existing config consumers / call sites] HIGH — Every component that reads config through the loader is in scope by dependency even though the plan changes none of them. Cost-of-error: any consumer expecting the old key names, old value types, or the old raise-on-miss breaks silently. Assumption that MUST be true: all existing config consumers are enumerated and compatible with both the new source and the new missing-key semantics.
- [scope:TOML parser dependency] MEDIUM-HIGH — Reading toml requires a wired, available parser (stdlib tomllib on 3.11+ or a third-party lib on older runtimes). Assumption that MUST be true: a TOML parser is present and importable in every target runtime/version; the dependency is declared in the project's install/requirements, not silently assumed.
- [scope:format/key migration mapping] MEDIUM-HIGH — Moving from the old config source to toml implies a key/structure mapping (flat→nested tables, type coercion: TOML is typed where the old format may have been all-strings). Cost-of-error: a key whose name or nesting changed now reads as 'missing' and — given the new behavior — silently takes a default. Assumption that MUST be true: every old key maps 1:1 to a toml key with matching type, and any renamed/nested key is migrated, not silently defaulted.
- [framing] MEDIUM-HIGH — Migration completeness / rollout: the plan states no data migration of existing user configs to the new toml format and no backward-compat read of the old source. Assumption: either existing deployments have their configs converted to toml as part of rollout, or a transition period reads both — otherwise every existing install loads all-defaults on upgrade. The 'how do current users get a config.toml' step is load-bearing and unstated.
- [scope:old config source / loader entry point] MEDIUM — The current loader and its old backing source are in scope as the thing being replaced. Cost-of-error: if other code still writes to or reads the old source directly (bypassing the loader), the migration leaves a split-brain config. Assumption that MUST be true: the loader is the sole read path for config and the old source is fully retired (or intentionally bridged).
- [scope:tests for config loader] MEDIUM — Existing tests are in scope: tests asserting that a missing key RAISES will now fail or, worse, were never written, so the behavior flip ships untested. Assumption that MUST be true: the test suite covers both the new toml-read path and the new missing-key-returns-default contract, and any old raise-on-miss test is intentionally updated rather than deleted to hide a regression.
- [framing] MEDIUM — 'Success: configs load from toml; missing keys use built-in defaults' is a happy-path success definition with no failure-mode criteria. Assumption: success should also pin down malformed-toml behavior, missing-file behavior, and unknown-key behavior. As written, an all-defaults load on a totally broken/absent file would technically pass the success check while being a silent outage.
- [scope:logging/observability for fallbacks] MEDIUM — With raise replaced by silent default, the only way a missing key surfaces is a log/metric. The plan provisions none. Assumption that MUST be true: there is (or will be) an observable signal — at minimum a debug/warn log — when a key falls back to default, so silent-misconfiguration is diagnosable in production.
