- [scope:settings.json hook registration] PreToolUse hook registration in settings.json must use the correct schema (nested {matcher, hooks:[{type:command, command}]}) and a matcher that actually fires on implementation-work tool calls (Edit/Write/Bash) — COST: if the registration is malformed or the matcher is wrong, the hook is silently dormant and NOTHING is blocked, so the entire feature ships broken while appearing installed. Is-it-actually-so: is the hook registered AND firing on real implementation events, not just present on disk?
- [scope:enforce-spec.sh exit-2 blocking semantics] enforce-spec.sh must exit 2 (not 0/1) on the block path AND Claude Code must honor exit 2 from a PreToolUse hook as a true block that prevents the tool call — COST: if exit 2 is not actually blocking for this hook event (e.g., PreToolUse treats nonzero differently, or stderr/exit contract differs), work proceeds despite no spec and the guarantee is false.
- [scope:spec marker / approved-spec detection] The 'spec marker' that signals an approved spec must exist at a known, stable path/format and be reliably detectable by the script (presence test + approval state, not just file existence) — COST: false-absent blocks ALL implementation work (self-lockout / total work stoppage); false-present lets unspecced work through (silent no-op). This is the highest-cost item: getting detection wrong breaks the harness in both directions.
- [scope:enforce marker / opt-in gate] The hook must be gated on a per-project enforcement marker (.claude/enforce) and fail-open when absent/unreadable — COST: without a fail-open opt-in gate, the hook blocks work in every project that installs the kit (including ones with no spec workflow), and an unreadable marker hard-locks the user. Is-it-actually-so: is the enforce marker shipped/created by the installer and reachable from the CWD the hook sees?
- [scope:hook CWD / project-root resolution] The hook must resolve the project root / marker path correctly regardless of the CWD Claude Code invokes it from (Claude Code does NOT guarantee CWD=project root) — COST: if the script looks for the spec/enforce marker via a bare relative path, it 404s from a non-root CWD and either fails-open (never blocks) or fails-closed (always blocks); a known prior defect class (Ph79 ${CLAUDE_PROJECT_DIR} fix).
- [scope:hook input parsing] The hook must parse the PreToolUse JSON stdin to identify the tool and target correctly (field path .tool_input/.input) and have its parser dependency (jq) available — COST: if input parsing fails or jq is missing, fail-open yields zero enforcement (silent) or fail-stop yields a hard lock on every tool call.
- [scope:installer wiring] The installer (install.sh --project-local / py-init / ts-init template copy) must actually distribute enforce-spec.sh, register it in settings.json, AND create the enforce marker — COST: a cascade-failure pattern where one missing install step (script not copied, marker not created) silently disables the whole gate; appears installed, enforces nothing.
- [scope:implementation-work classification] The hook must correctly distinguish 'implementation work' from non-implementation tool calls (planning reads, the /spec write itself, doc edits, the spec file write that creates the marker) — COST: if classification is too broad it deadlocks the very act of writing the spec (you can't create the spec because no spec exists); too narrow and real implementation slips through.
- [framing] Is this problem worth solving — does unspecced implementation actually cause enough harm to justify a hard block, versus an advisory nudge? A blocking gate is the most expensive intervention; the plan assumes hard-block is the right severity rather than warn-and-proceed.
- [framing] Is a deterministic hook the right substrate? The plan assumes a CWD-dependent, fail-open shell hook can reliably enforce a workflow invariant — but every prior enforcement hook in this codebase has had a silent-breakage / cascade-failure history (pre-compact, MCP CWD, nana-init). The framing assumes hooks enforce reliably when the project's own evidence says they often ship dormant.
- [framing] The success criterion ('work without an approved spec is blocked') will be verified by FIRING the hook on a real event (pipe input, assert exit 2), not by file presence — the plan's success statement is observational and assumes someone confirms live blocking; if validated only by 'hook is registered', it ships broken.
- [framing] Will the gate survive its own escape hatches — does blocking ALL implementation work without a spec hold up against legitimate exceptions (security hotfix, dependency prereq, user override)? The plan assumes a blanket block is acceptable, but the harness's own rules carry escape hatches that a naive exit-2 gate would contradict.
