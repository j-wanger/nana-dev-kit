- [scope:memory-db-persistence] HIGH — if the DB does not persist at the path the server actually uses, cross-session recall silently returns nothing and the entire success criterion fails. The MCP server's working directory must resolve to the location where the DB file is created/read, and that path must be stable across sessions (not a transient CWD or temp dir). [is-it-actually-so] The store must persist at the path we think — prior project history shows Claude Code ignores settings.json `cwd` and uses the project directory, so the DB lands at <project_root>/.memory/memory.db, NOT ~/.claude/.memory/; a wrong path assumption yields a fresh empty DB every session that reads/writes succeed against but never recall across boundaries.
- [scope:mcpServers-registration] HIGH — if the server entry in settings.json is malformed, points at a wrong cwd, or is placed at the wrong scope, the MCP server never starts and memory_store/memory_search are unavailable; the plan assumes a single registration line works, but registration must use an idempotent JSON merge (no settings.json / existing-without-mcpServers / existing-with-mcpServers cases) and the cwd must point at ~/.claude (the parent), not the package dir — this exact bug was broken since an early phase.
- [scope:python-module-launch] HIGH — `python -m memory_server` must actually import and run: the module must be on PYTHONPATH/installed in the interpreter Claude Code invokes, the right Python (venv vs system) must be selected, and runtime deps must be present; if the import fails the server dies on launch and the agent sees no memory tools, with failure likely silent at the MCP layer. The plan assumes the launch command is wired and importable — it must be verified with an import check after registration, not assumed.
- [scope:mcp-server-runtime-health] HIGH — the server process must stay up across the whole session and respond to stdio MCP calls; a server that registers but crashes or hangs presents as 'tools missing' or 'calls error' with no obvious cause. Must verify the server is actually running (live tool call), not merely registered.
- [scope:cross-session-recall-verification] HIGH — the success test ('recorded in one session, recalled in the next') must exercise a genuinely NEW session (fresh process/DB connection), not the same session's in-memory state; if the verification reuses session state it will pass while the real persistence path is broken. Recall also depends on search retrieving by semantic/keyword match, not just exact storage — memory_search must return the stored decision given a reasonable query.
- [scope:memory-tool-availability] HIGH — memory_store and memory_search must be exposed to the agent as callable tools in a normal session (correct tool names, surfaced by the running MCP server); if the tools aren't registered/visible the agent cannot record or recall regardless of DB health.
- [scope:health-probe-correctness] MEDIUM — any health probe used to confirm 'memory works' must check the correct DB path and correct schema column (e.g. `active` vs `is_active`); a probe checking the wrong path/column reports broken-when-healthy or healthy-when-broken, masking the real persistence state. (Prior probe checked the wrong path AND wrong column.)
- [scope:settings-json-integrity] MEDIUM — editing settings.json to add the server must not corrupt or drop existing keys (other mcpServers, hooks, env); a clobbering edit breaks unrelated harness behavior. Use a merge, not a hand-edit/overwrite.
- [scope:db-schema-migration] MEDIUM — the DB the server opens must have the schema the server code expects; a stale/incompatible DB at the resolved path causes read/write errors or silent column mismatches even when the path is correct.
- [scope:store-dedup-behavior] LOW-MEDIUM — store() applies dedup/reinforce/warn logic; a near-duplicate decision may be reinforced/merged rather than stored verbatim, so the recall test should tolerate normalized/deduped content rather than expect byte-identical recall.
- [framing] HIGH — will the measured effect replicate / is this the right substrate? Documented prior measurement (the amplifier program: Ph70/71/77/78) found NULL harness headroom in re-presenting decisions the model can recover from code+tests across sessions — cross-session decision retention residual was 0/14. The framing assumption that 'recall across sessions' delivers value must hold despite evidence that decision recall is largely recoverable without the memory store; the value, if any, lives in genuinely proprietary/post-cutoff content the model can't re-derive.
- [framing] MEDIUM — is this problem worth solving now? The plan assumes MCP memory is the right layer for cross-session decision persistence, but the project's own memory-architecture classification rates MCP memory as VOLUNTARY (nudges only) and treats always-loaded .claude/rules/ files + dev-wiki as the mandatory/automatic durable layers; relying on a voluntary, historically-fragile layer for a stated success criterion may be solving the wrong substrate.
- [framing] MEDIUM — is the success criterion sufficient? 'A decision recorded in one session is recalled in the next' assumes a single round-trip proves durability, but it doesn't establish persistence across process restarts, machine reboots, path changes, or schema upgrades — a one-shot pass can hide a path/CWD bug that surfaces later (the cascade-failure anti-pattern: a silent install/path gap disables the feature for many phases before anyone notices).
- [framing] LOW-MEDIUM — does this earn its complexity (subtraction test)? Standing up and maintaining an MCP server + DB adds a continuously-running dependency with multiple silent-failure modes; the framing assumes the recall benefit outweighs the operational fragility versus simpler durable stores already in use (.claude/rules/, dev-wiki) that load deterministically.
