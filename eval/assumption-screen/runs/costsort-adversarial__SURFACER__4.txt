- [scope:default-fallback-behavior] HIGH (silent-failure / data-integrity): swallowing missing keys into built-in defaults removes the only signal that a key is missing or misspelled — a typo'd or omitted critical key now silently runs on a default (wrong port, wrong DB, auth disabled) instead of failing loudly. The plan must assume NO config key is safety-critical enough that a silent default is worse than a crash — but plausibly some are. This 'minor cleanup' inverts the loader's error contract.
- [scope:default-fallback-behavior] HIGH: built-in defaults must EXIST and be correct/safe for EVERY key that can be missing — the plan assumes a complete, audited default set; if a key has no sensible default (e.g. a secret, an endpoint) the fallback returns a meaningless or insecure value rather than erroring.
- [scope:existing-callers / consumers of the loader] HIGH (behavioral regression): every existing caller must tolerate the new never-raise contract — code that today relies on a KeyError/exception to detect misconfiguration (try/except, fail-fast startup checks) will now silently proceed with a default, so the plan assumes no caller depends on the raise behavior.
- [scope:config-data-migration] HIGH (no migration path stated): the plan assumes existing config data is migrated into config.toml — but states no conversion of the OLD format to TOML and no dual-read/transition window; if the old file isn't translated, EVERY key reads as 'missing' and (thanks to the cleanup) silently falls back to defaults, masking a total config loss as a successful load.
- [scope:config.toml file] HIGH: config.toml must actually EXIST at the path the loader looks for, be readable, and be valid TOML — the plan assumes a discoverable, well-formed file; a missing file, wrong search path, or parse error has no defined behavior (and may itself collapse to all-defaults under the new fallback rule).
- [scope:TOML type model] HIGH: TOML's type system (no nulls, typed ints/floats/dates/arrays/tables, strict quoting) must faithfully represent every value the old format carried — the plan assumes lossless round-trip; values like null, heterogeneous lists, or stringly-typed numbers may change type or be unrepresentable.
- [scope:TOML parser dependency] MEDIUM: a TOML parser must be available and wired in (Python <3.11 has no stdlib tomllib; writing TOML needs a separate lib) — the plan assumes the dependency is present, on the target runtime version, and added to the project's deps/lockfile.
- [scope:tests] MEDIUM: existing config-loader tests must be updated for the new format AND the inverted error contract — any test asserting 'raises on missing key' will now fail or, worse, was never written; the plan assumes test coverage exists for both the toml read path and the default-fallback path.
- [scope:secrets/sensitive-config handling] MEDIUM: if secrets currently live in config, moving them into a plaintext config.toml must not change how they're stored/loaded/secured — the plan assumes no secret-management interaction and that defaulting a missing secret to a built-in value is acceptable (it usually is not).
- [scope:config schema / key-name stability] MEDIUM: TOML's nested-table/dotted-key structure must preserve the exact key names and nesting the loader's lookups expect — the plan assumes a 1:1 key mapping so existing get('section.key') style accesses still resolve.
- [framing] Bundling the error-contract change as 'minor cleanup while we're in here' is the riskiest assumption: a silent behavior inversion (raise -> default) is being smuggled into a format-migration phase with no isolated test or measurement; it deserves its own decision, not a ride-along. Subtraction test: does the cleanup earn its risk inside this phase?
- [framing] Assumes 'smoother for users' is the right goal — but fail-soft on config is often worse than fail-fast for operators; the real users (operators debugging a misconfig) may strongly prefer a loud error. The benefit is asserted, not measured.
- [framing] Assumes TOML is the right substrate for this config — the plan gives no reason TOML beats the current format (or YAML/JSON/env); migration cost is real and the payoff is unstated.
- [framing] Success criteria are too weak to be load-bearing: 'configs load from toml; missing keys use defaults' verifies the happy path but asserts nothing about round-trip fidelity, malformed-file behavior, or that no critical key silently defaults — passing these criteria does not mean the migration is safe.
