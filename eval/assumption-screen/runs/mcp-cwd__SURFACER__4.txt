- [scope:memory-db-persistence] The memory store must persist to a stable, consistent path across sessions; if the DB is created at a different working directory than the one it's read from (the documented CWD-mismatch failure class), session 1's write and session 2's read hit different files and recall silently returns nothing — this is the single highest cost-of-error item because the success criterion (recall across sessions) fails with no visible error.
- [scope:server-launch-command] `python -m memory_server` must actually resolve and start — the `memory_server` module must be importable on the PATH/venv that settings.json launches, with all its dependencies (e.g. sqlite) installed; if the module isn't found or a dep is missing the server dies on spawn and every memory_* call fails, defeating the whole plan.
- [scope:mcp-server-cwd] The MCP server's effective working directory must be the one the plan assumes (parent dir, not the package dir) so the DB lands where reads expect it; Claude Code is documented to ignore settings.json `cwd` and use the project directory, so the configured cwd may be silently overridden — wrong CWD => store/recall split-brain.
- [scope:settings.json-registration] The mcpServers block in settings.json must be schema-valid and merged idempotently (correct command/args/cwd/env shape) without clobbering existing entries; a malformed or overwriting edit either fails server registration or breaks other already-registered MCP servers/hooks.
- [scope:memory-store-write-durability] memory_store must actually commit a durable row that survives process exit (DB file flushed/closed, not just held in an ephemeral in-memory handle); if the write isn't durably persisted before the session ends, the next session has nothing to recall even with a correct path.
- [scope:memory-search-recall] memory_search must retrieve the stored decision with the query the next session will plausibly use — recall depends on the search/index matching, not just the row existing; if FTS/embedding indexing or the query path differs from what was written, the row exists but is not returned, and the success test fails.
- [scope:cross-session-isolation-scope] The memory scope (project vs global) must be consistent between the storing session and the recalling session; if session 1 stores at one scope and session 2 searches another, or project-dir-derived scoping differs, recall misses despite a durable write.
- [scope:agent-tool-availability] The agent must actually be offered and willing to call memory_store/memory_search in a normal session (tools surfaced after registration + restart, not deferred/unloaded); if the tools aren't wired into the agent's tool set or require a restart not performed, 'confirm the agent can call' never happens.
- [scope:embedding-provider] If recall relies on vector/semantic search, the embedding provider/model must be available and produce vectors matching the index dimensions; absent embeddings the system must fall back to word-overlap/FTS recall — if neither path is wired, search returns empty.
- [framing] The problem is worth solving — cross-session decision recall via an MCP memory store adds enough value over the alternatives (re-deriving from code/tests, dev-wiki, .claude/rules files) to justify a stateful sidecar; prior measurement in this kit found cross-session decision retention NULL (every decision recoverable from code+tests), so the assumed value may not exist.
- [framing] MCP memory is the right substrate — a voluntary, nudge-driven store is more reliable than the always-loaded mandatory layers (.claude/rules/) for surviving across sessions; if the agent doesn't reliably call store/search unprompted, the voluntary layer under-fires and recall is incidental.
- [framing] A single recorded-then-recalled decision is a sufficient acceptance test — the success criterion generalizes to real multi-session use and isn't a one-off pass that masks variance, indexing gaps, or scope/CWD edge cases that only surface at volume.
- [framing] 'Normal session' confirmation reproduces real usage — that the confirmation session and a genuine future session share the same project dir, scope, restart state, and tool availability, so a green confirmation actually predicts recall in the wild.
