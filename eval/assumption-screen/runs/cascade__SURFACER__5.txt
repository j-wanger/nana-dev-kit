- [scope:enforce-spec.sh] The block must be reversible/non-self-locking: the gate must NOT prevent the actions needed to satisfy it (writing the spec, adding the marker, editing enforce-spec.sh itself), or the project enters deadlock with no escape — this is the single highest cost-of-error and demands tmpdir/hermetic testing before touching live state.
- [scope:enforce-spec.sh] enforce-spec.sh must fail-OPEN on its own errors (missing jq, malformed stdin JSON, missing marker file, unreadable path): a hook that errors-then-blocks halts ALL tool use; the script must exit 0 (allow) on any internal failure, never exit 2.
- [scope:settings.json PreToolUse registration] The hook must actually be REGISTERED AND FIRING in the consuming project, not merely present on disk — a registered-but-dormant or unregistered hook passes a file-presence test yet ships broken; verification must pipe a real PreToolUse event and assert exit 2, not check file existence.
- [scope:settings.json PreToolUse registration] The settings.json hook schema must be the nested {matcher, hooks:[{type:'command', command:'...'}]} form Claude Code validates; a legacy flat {matcher, command} entry passes /doctor as an error and the hook never runs.
- [framing] The exit-2 PreToolUse contract must hold: Claude Code must interpret PreToolUse exit code 2 as 'block the tool call and surface stderr to the model.' If exit 2 is not the block signal for PreToolUse (vs another hook event), the entire mechanism is a no-op.
- [scope:implementation-work matcher] The PreToolUse matcher must correctly DISCRIMINATE implementation work from non-implementation work — broad enough to catch Edit/Write to code, narrow enough to exempt spec-writing, marker creation, and hook edits — or it either deadlocks the spec workflow or lets implementation through ungated.
- [scope:spec marker] The marker semantics (what counts as 'approved spec') must be unambiguous and match what producers actually write — e.g. an HTML approval comment OR exit-criteria presence — including backward-compat for marker-less legacy specs; otherwise the gate either blocks valid specced work or waves specless work through.
- [scope:spec marker] The marker must persist at the exact path/location the hook reads (CWD-relative .claude/ vs project-root vs spec-file-internal), resolved correctly even when Claude Code runs the hook from a non-root CWD; a path mismatch means the marker is never found and all work is blocked.
- [scope:hook installer/distribution] The hook must be installed into the consuming project by some delivery path (template copy / install.sh --project-local / per-project init) with correct path resolution; the success criterion 'in a consuming project, work is blocked' is unmeetable if the install/distribution step and its path-resolution are silently assumed rather than wired.
- [scope:enforce marker (.claude/enforce)] The gate should be gated by a per-project (or global) enable marker so it only fires where opted-in; without this check the hook over-reaches and blocks work in every project that has the kit installed, including projects that legitimately don't use specs.
- [framing] Hook-based enforcement must be durable, not silently unwireable — prior project history shows ~3 cascade failures where a missing install step disabled enforcement entirely; the plan assumes the activation point holds, but always-loaded rules files have historically been more reliable than added hooks.
- [framing] A hard PreToolUse BLOCK (exit 2) is the right intervention strength versus an advisory nudge; blocking is high-friction and risks false-positive lockouts, and the plan assumes the spec-discipline problem is severe enough to justify the strictest mechanism rather than a warn-only hook.
- [framing] Tool-use interception is the right SUBSTRATE for enforcing spec discipline at all — i.e. spec-skipping is best caught at the Edit/Write boundary rather than at a workflow/skill boundary (e.g. inside dev-plan/spec), and a deterministic file-marker check is the right detector rather than judging 'is this implementation' semantically.
- [framing] The problem is worth solving: developers actually skip the spec step often enough that an automated gate earns its complexity and maintenance cost (and the per-task false-block friction) over relying on the existing spec-always-mandatory convention.
- [framing] The success criterion ('work without an approved spec is blocked') is the right thing to measure — it verifies the block fires but does NOT verify the inverse (that approved-spec work proceeds unblocked) nor that the spec-writing escape path stays open; the plan assumes one-directional verification is sufficient when the costly failure modes are on the un-measured side (over-blocking / lockout).
