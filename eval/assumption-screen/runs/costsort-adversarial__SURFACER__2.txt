- [scope:missing-key-default-semantics] HIGH — The cleanup silently changes failure semantics from raise-on-missing to return-default. Must be true: NO current caller depends on the loader RAISING on a missing key (e.g. as a required-config guard, fail-fast validation, or a try/except that triggers fallback logic). Cost of error: a genuinely-missing critical key (DB URL, secret, auth toggle) now silently resolves to a default, turning a loud startup failure into a silent misconfiguration that surfaces later in production.
- [scope:built-in-defaults] HIGH — Must be true: a complete, correct built-in default EXISTS for every key that can be missing, and each default is SAFE to use in production (not a dev placeholder, not an insecure-open value like debug=true / auth=off / wide-open CORS). Cost of error: a missing security- or correctness-sensitive key falls back to an unsafe or wrong default with no signal.
- [scope:config.toml-format-and-parser] HIGH — Must be true: a TOML parser is available/wired (e.g. tomllib on the runtime's Python version, or a declared dependency) and the new config.toml is valid, well-formed, and type-correct (TOML's typed scalars map cleanly onto what the code expects). Cost of error: loader raises on parse/type errors at startup, or coerces types wrongly (e.g. a port read as string), breaking the app for every consumer.
- [scope:config-value-migration] HIGH — Must be true: every key/value from the OLD config source is actually PRESENT in the new config.toml (a real migration of data, not just a format switch). Cost of error: combined with the new return-default behavior, any key forgotten during migration is masked — it won't raise, it'll silently use a default, so the migration gap is invisible. The two changes interact dangerously: the cleanup hides exactly the mistakes the migration is most likely to make.
- [framing] HIGH — Is bundling an unrelated behavior change (raise→default) into a format-migration the right move? These are independent changes with independent blast radii; bundling them means the silent-default change ships under cover of 'minor cleanup' without its own justification, test coverage, or review scrutiny — and makes migration data-loss undetectable. They should likely be separate, individually-reversible changes.
- [scope:old-config-source-and-callers] MED — Must be true: the prior config source/format and its loader entry points are identified, and all call sites of the config loader are known and updated to the new path/API. Cost of error: some code path still reads the old source (stale values) or calls a removed/changed loader signature, causing partial migration where some components run on old config.
- [scope:config.toml-path-and-discovery] MED — Must be true: the loader looks for config.toml at the correct, agreed location and that path is consistent across local/dev/CI/prod environments (and packaged/installed layouts). Cost of error: file-not-found at runtime; with return-default semantics this may degrade to 'everything uses defaults' silently rather than failing loudly.
- [scope:tests] MED — Must be true: existing config tests are updated for both the new source and the new missing-key semantics, AND a test asserts the new default-on-missing behavior (and that previously-required keys are flagged some other way). Cost of error: regression on either change ships undetected; tests that previously asserted 'raises on missing' now must be deliberately changed, not accidentally left passing/failing.
- [framing] MED — Will 'smoother for users' actually be a net improvement, or does it trade a clear early error for a confusing late one? The asserted benefit (smoother) assumes users prefer silent defaults to explicit errors; for required configuration the opposite is usually true. The user-value claim is unmeasured and may be net-negative.
- [scope:default-precedence-and-partial-config] MED — Must be true: the resolution order is well-defined when a key is present-but-empty, present-but-null, or partially specified (not just fully-missing) — i.e. what counts as 'missing' is unambiguous. Cost of error: ambiguous cases (empty string, null, 0/false) get inconsistently treated as missing-or-not, producing surprising values.
- [scope:env-var-and-override-layering] LOW — Must be true: if config was previously overridable via env vars / CLI / layered sources, that override layering still composes correctly with the new toml source and default fallback. Cost of error: deployment-time overrides stop taking effect, silently reverting to file or default values.
- [framing] LOW — Is config.toml the right substrate vs the current format? The plan assumes TOML is the correct target; if the existing format supported comments/interpolation/multi-doc features TOML lacks (or vice versa), the migration may lose expressiveness. Substrate choice is asserted, not justified.
