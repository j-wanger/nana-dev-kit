- [scope:PreToolUse-hook-firing] (HIGH — if the hook is registered but not actually firing, ALL implementation work proceeds unguarded and the enforcement is silently dead; this is the kit's documented dominant failure class — registered-but-dormant) The enforce-spec.sh hook must be genuinely WIRED and FIRING on the relevant tool events in the consuming project, not merely present in settings.json — verified by piping a real PreToolUse event and asserting exit 2, never by file/registration presence alone.
- [scope:exit-code-2-semantics] (HIGH — if exit 2 does not actually block, or PreToolUse exit codes differ from assumption, the gate is a no-op while appearing installed) PreToolUse exit 2 must in fact BLOCK the tool use (Claude Code honors exit 2 as block on PreToolUse, surfaces stderr) — not just warn or be ignored — for the stated success criterion 'work is blocked' to hold.
- [scope:spec-marker-detection] (HIGH — a wrong marker path/column/format means the hook either always-blocks legitimate work (false lockout) or never-blocks (always-open); both defeat the feature) The 'spec marker' the hook checks for must exist at a known, correct path/format in the consuming project, and the absence/presence test must match how approved specs actually record approval (e.g. nana:approved HTML comment OR exit-criteria) — including backward-compat for pre-existing marker-less specs.
- [scope:fail-open-vs-fail-closed] (HIGH — a hook that errors hard, or that locks the agent out of its own fix, is worse than no hook; kit history shows enforce-spec self-lockout regressions) enforce-spec.sh must fail SAFELY: it must not crash the session or block on its own dependencies being missing (jq/path), and a misfire must not lock the user out of editing the very files needed to add a spec or fix the hook (tmpdir-tested before touching live state).
- [scope:tool-matcher-scope] (HIGH — if the PreToolUse matcher targets the wrong tools, it either blocks reads/benign ops (false positives, user disables it) or misses Edit/Write (lets real implementation through)) The hook's matcher must precisely scope 'implementation work' to the right tools (Edit/Write/Bash-that-implements) and EXCLUDE benign operations, so it blocks the intended actions without false positives that drive users to uninstall it.
- [scope:settings.json-registration-source] (MEDIUM — hand-editing a generated settings.json gets clobbered on regeneration; drift test fails) Registration must go through the single source of truth (modules.json → register-settings.py / make template), not a hand-edit of the generated settings.json, or the hook registration will drift/disappear and the drift test will flag it.
- [scope:project-opt-in-marker] (MEDIUM — without a per-project enforce marker the hook is either globally coercive or silently disabled) The hook must gate on a project-reachable enforce marker (.claude/enforce or $HOME/.claude/enforce) so enforcement is opt-in per project; if the marker is missing the cascade is silent total disablement (documented anti-pattern: marker-missing → all enforcement off).
- [scope:install-distribution] (MEDIUM — if enforce-spec.sh and its marker aren't shipped/installed by the installer + template, the consuming project never receives a working hook) The hook script, its settings registration, AND the enforce marker must all be distributed to the consuming project by the installer/template path (py-init/ts-init copy or install.sh --project-local), or 'in a consuming project it is blocked' is unverifiable.
- [framing] (HIGH — if a strong agent already volunteers a spec / the open-ended-prompt and existing 2-gate ceremony already secure spec discipline, a blocking hook may add coercion and false-lockout cost for ~0 marginal compliance lift — the kit's measured pattern is that re-presenting/forcing what the model does unprompted yields NULL value) The problem must be worth solving: spec-less implementation work must actually occur often enough, and be costly enough, that a hard PreToolUse BLOCK beats the existing softer gates (spec skill, direction/delivery gates) net of false-positive friction.
- [framing] (MEDIUM — a hard block is the heaviest substrate; an advisory/exit-0 nudge or a Stop-prompt review may capture most of the value without lockout risk) A hard blocking hook (exit 2) must be the right SUBSTRATE versus a non-destructive advisory or a review-at-Stop gate — i.e. the cost of occasionally-wrong blocking is justified rather than fail-open warning.
- [framing] (MEDIUM — 'blocked in a consuming project' shown once is an n=1 demo, not a banked effect; firing can regress silently across phases as it has repeatedly) The success demonstration must REPLICATE and PERSIST: a one-time observed block is not evidence the gate stays wired across reinstalls/regenerations — caps and enforcement need standing test assertions, not a single manual confirmation.
