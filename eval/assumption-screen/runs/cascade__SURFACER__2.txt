- [scope:settings.json hook registration] PreToolUse hook registration in settings.json must be the live, loaded config the consuming project's Claude Code actually reads at runtime — if the entry is malformed, in the wrong settings file (project vs user vs local), or in the wrong schema (nested {matcher, hooks:[{type:command, command}]} vs legacy flat), the hook never fires and ALL blocking silently fails open. WORST cost: the entire feature is a no-op while appearing installed.
- [scope:enforce-spec.sh exit-2 contract] The block path depends on Claude Code honoring PreToolUse exit code 2 as 'block tool use'. If exit 2 does not actually halt the implementation tool (wrong stream, exit 2 not treated as block for this hook event, or stderr ignored), unspecced work proceeds — the core promise breaks while the script 'runs successfully'.
- [scope:hook installation/delivery into consuming project] enforce-spec.sh must be physically installed AND registered in the consuming project (via installer/template copy), not just authored in the kit. The cascade-failure class (installer cp -r missing a file → marker/hook absent → enforcement silently disabled) means an uninstalled-but-assumed-present hook passes a presence check and ships broken. Is it actually installed and firing in the consumer?
- [scope:hook command path resolution] The registered hook command path must resolve when Claude Code invokes it from a non-root CWD. A bare-relative `.claude/hooks/enforce-spec.sh` 404s when CWD != project root (documented prior defect); needs ${CLAUDE_PROJECT_DIR}/$HOME absolute resolution or the hook is unreachable and fails open.
- [scope:spec marker detection] The 'spec marker' the hook tests for must exist, be at the path/format the hook checks, and correctly represent approval. If marker semantics are wrong (checks presence only, or wrong file/column/comment), an unapproved or marker-less spec is treated as approved (false-allow) OR a legitimately-approved spec is missed (false-block). Backward-compat for pre-existing marker-less specs is unaddressed.
- [framing] The PreToolUse hook (deterministic boundary validator) is the right substrate for spec enforcement vs a skill/instruction-level gate — but it assumes the consuming project has a `.claude/enforce` (or global) opt-in marker; without project-reachable enforcement opt-in, the hook is dormant-by-design and the feature does nothing. Is enforcement even enabled?
- [scope:implementation-tool detection / matcher scope] The hook's PreToolUse matcher must correctly classify which tool calls constitute 'implementation work' (Edit/Write/Bash?) and ONLY those. Too broad → blocks reads, planning, spec-writing itself (deadlock: can't write the spec because no spec exists); too narrow → implementation slips through unblocked.
- [framing] Blocking is the right enforcement modality vs advisory/fail-open. The kit's stated discipline is fail-open / non-destructive for hooks; a hard exit-2 block is a fail-CLOSED design that can self-lockout (e.g. blocks the very act of authoring/approving the spec). Assumes hard-block net-helps rather than creating an unescapable gate.
- [scope:functional verification / test] 'Success: work without an approved spec is blocked' must be verified by piping a real PreToolUse event and asserting exit 2 (firing test), in a hermetic tmpdir — not by file/registration presence. Assumes a behavioral test exists; presence-only verification is the documented way this class of hook ships broken.
- [framing] The problem is worth solving at the hook layer at all — assumes unspecced implementation is a real, recurring failure mode in the consuming project AND that a blocking gate changes behavior rather than just being bypassed/disabled by frustrated users (the measured effect must replicate beyond the author's own project).
- [scope:settings.json drift / single-source-of-truth] settings.json must stay consistent with the kit's registration source-of-truth (modules.json) — if settings.json is hand-edited rather than regenerated, a drift test should fail; assumes the registration is wired through the canonical generator, not a one-off hand edit that later gets clobbered.
- [scope:spec-authoring escape path] There must be a way to create the approving spec while the block is active (the spec skill / spec-writing tools must be exempt from the matcher). Assumes a bootstrap exemption exists; otherwise the gate is unsatisfiable on a fresh project.
