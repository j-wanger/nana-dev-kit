- [scope:MCP-memory-server-config-path] COST: catastrophic — if the probe reads server config from the wrong path (e.g. ~/.claude vs project_root/.memory), it reports 'broken'/'not-configured' on a healthy store or 'healthy' on a dead one; every session then opens with a false memory-health line, the exact opposite of Success. ASSUMPTION: the config the probe reads (settings.json .mcpServers.memory) must point at the same path the server actually uses at runtime, AND that path must be where the DB persists. (Project history shows Claude Code ignores settings.json cwd and uses project_root/.memory/memory.db — so 'read the server config' is not sufficient to locate the store.)
- [scope:memory-DB-store-path-persistence] COST: catastrophic — if the DB the probe inspects is not the DB the server writes to, the sqlite3 entry count is meaningless and 'healthy (N entries)' is a lie. ASSUMPTION: the SQLite DB must exist and persist at the exact path the probe queries, with the schema/column the probe expects (the active vs is_active column mismatch silently zero-counts or errors).
- [scope:session-start.sh-hook-installed-and-firing] COST: high — if session-start.sh is not actually registered/firing (it is a --project-local hook, not globally installed by default), the probe runs never, and NO session gets a memory-health line; Success is unreachable regardless of probe correctness. ASSUMPTION: session-start.sh must be installed AND firing on session start in the consuming project (presence in templates ≠ wired). Verify by piping a real SessionStart event and asserting output, not by file presence.
- [scope:probe-fail-open-behavior] COST: high — session-start hooks gate session readiness; if the probe errors (missing sqlite3, missing jq, malformed config) and does not fail-open (exit 0), it could degrade or block every session start. ASSUMPTION: the probe must fail-open and degrade to an honest 'broken'/'not-configured' line on any internal failure, never abort the hook or emit a false 'healthy'.
- [scope:health-state-accuracy-3-state] COST: high — Success demands an ACCURATE line; a probe that can only check file existence (config present) but not liveness will report 'healthy' for a registered-but-dead server. ASSUMPTION: the 3-state classifier (healthy/broken/not-configured) must distinguish 'configured but non-functional' from 'configured and working' — i.e. it must verify the server actually responds / the import works / the DB is readable, not just that config exists.
- [scope:probe-dependencies-jq-sqlite3] COST: medium-high — the probe needs jq (to read settings.json) and sqlite3 (to count entries) and the MCP command to import-check; if any is absent on the consuming machine the probe cannot determine true state. ASSUMPTION: jq, sqlite3, and the memory MCP command must be present and on PATH in the session-start environment, or the probe must classify their absence as a distinct honest state rather than mislabeling.
- [scope:session-start.sh-line-budget] COST: medium — session-start.sh has a documented line cap (eroded silently 70→137 in the past); adding a probe + nudge inflates an always-run hook and risks tripping a context/size budget or re-introducing cap erosion. ASSUMPTION: the added probe + memory-nudge must fit within session-start.sh's line/size budget, with a test asserting the cap (caps need assertions, not just documentation).
- [scope:memory-nudge-reminder] COST: medium — the nudge is a voluntary behavioral reminder; if it fires unconditionally even when memory is 'not-configured' or 'broken', it nags the agent to use a tool that doesn't work. ASSUMPTION: the nudge must be gated on the probe's health state (only remind to use memory when memory is actually healthy/usable), and must be advisory-only.
- [framing] Is an at-session-start memory-health LINE worth solving, or process-theatre? The plan assumes the agent reading a startup status line changes behavior. If the agent ignores it or it adds noise to every session, the feature costs context budget for zero behavior change. Burden-of-proof on the feature: measure whether the line actually changes memory usage before banking it.
- [framing] Is a startup PROBE the right substrate, vs fixing the underlying config so memory just works? The plan treats reporting health as the goal; but project history shows the real defect was a CWD/path mismatch that made memory silently dead for many phases. A probe that accurately reports 'broken' every session is a worse outcome than fixing the path so it reports 'healthy'. ASSUMPTION: surfacing health is the right intervention rather than repairing the root cause.
- [framing] Will 'accurate' survive contact with reality? The plan assumes the probe CAN be accurate, but accuracy depends on the probe and the server agreeing on path/schema — an alignment that has broken silently before. If they can drift independently (config edited, server cwd differs), the probe's accuracy is not a banked property and will rot without a drift test pinning probe-path == server-path.
- [framing] Is 'every session begins with an accurate memory-health line' verifiable, or self-asserting? Success has no measurable acceptance beyond the line appearing. ASSUMPTION: there exists a deterministic test (hermetic mktemp env, piped SessionStart event) that asserts the line's CONTENT matches a known store state across all 3 states — otherwise Success is unfalsifiable and the feature can ship broken.
