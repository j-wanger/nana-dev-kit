- [scope:MCP-memory-server-config-path] HIGH — cost: if the probe reads the wrong config location (or the server's CWD/DB path differs from what the probe checks), it reports a false health state — worse than no probe, since an authoritatively-wrong 'healthy' line erodes trust in every subsequent session. Assumption: the server config the probe parses (settings.json .mcpServers.memory) is the same authoritative source the live MCP server actually uses, and the DB it points to is at the path the probe inspects.
- [framing] HIGH — cost: the entire feature is wasted if the agent does not act on a memory-health line. Assumption: surfacing memory health at session start changes agent behavior (e.g. triggers memory_search, or warns before relying on memory) — a passive status line that no one reads/acts on is process theatre.
- [scope:health-state-accuracy-definition] HIGH — cost: 'healthy / broken / not-configured' is a 3-state classifier; if the boundaries are wrong (e.g. configured-but-empty, configured-but-unreachable, schema-mismatch), it mislabels states and the success criterion 'accurate' is unmet. Assumption: these three states are exhaustive and each maps to a deterministic, observable signal (config present + server importable + DB reachable + entries countable) rather than a guess.
- [scope:session-start.sh-hook-installed-and-firing] HIGH — cost: if session-start.sh is not actually registered/firing in consuming projects (it is a --project-local opt-in hook, not globally installed), the probe never runs and ZERO sessions get the line — success ('every session begins with...') is structurally unreachable. Assumption: session-start.sh is installed and fires on SessionStart in the environments where the line is promised.
- [framing] HIGH — cost: if the memory layer is voluntary/nudge-only and rarely used, a startup health probe solves a low-value problem at the cost of always-loaded startup latency and output noise. Assumption: memory-health is a problem worth a per-session probe — the failure it guards against (silently-broken memory) is both frequent and costly enough to justify standing instrumentation.
- [scope:session-start.sh-line/size-budget] HIGH — cost: session-start.sh has a documented line cap (eroded 70→137 before, fixed by extraction); adding a probe + nudge inline can re-breach the cap or bloat always-loaded startup output, regressing the very hygiene other phases enforced. Assumption: the new probe + nudge fit within session-start.sh's enforced budget, or are extracted to a companion (cognitive-readiness.sh pattern) with a test asserting the cap.
- [scope:probe-fail-open-behavior] HIGH — cost: if the probe errors (missing jq/sqlite3/python, malformed config) and is not fail-open, it can abort session-start and break startup entirely — catastrophic vs. the small benefit. Assumption: the probe is fail-open (exit 0, degrade to 'unknown/not-configured' on any tool or parse error) and never blocks the session.
- [scope:memory-DB-persistence-path] HIGH — cost: the known CWD-mismatch bug (DB at <project_root>/.memory/memory.db, not ~/.claude/.memory/; prior probe checked wrong path AND wrong column is_active vs active) means a naive probe reports 'broken' on a healthy store or vice-versa. Assumption: the probe inspects the correct DB path AND the correct schema/column the live server writes.
- [scope:config-read-dependencies-wired] MEDIUM — cost: 'read the server config' assumes a JSON parser (jq) and a DB reader (sqlite3) and the MCP import-check command are present on the host; if absent the probe can't classify and either errors or always reports not-configured. Assumption: the probe's runtime dependencies are guaranteed installed by the same path that installs the hook (install.sh), or handled gracefully when missing.
- [scope:memory-nudge-reminder] MEDIUM — cost: a nudge that fires unconditionally (even when memory is not-configured/opt-out) is noise that trains the agent/user to ignore startup output, degrading signal for the rest of the line. Assumption: the nudge is state-gated (only when memory is configured + healthy and there is actually something to search) and is advisory, not enforcing.
- [framing] MEDIUM — cost: the plan conflates two features (health probe + behavioral nudge) under one success metric; if only the probe is needed, the nudge adds complexity that fails the subtraction test. Assumption: both the probe AND the nudge independently earn their complexity, rather than the nudge being bundled scope that should be cut/deferred.
- [framing] MEDIUM — cost: 'accurate memory-health line' is asserted, not measured; if there is no test piping a real SessionStart event and asserting the emitted line per state, the feature can ship silently broken (the recurring dormant-hook failure mode in this codebase). Assumption: accuracy is verified by a hermetic firing test (real event in, expected line out) across all three states — not by file-presence alone.
- [scope:settings.json-single-source-of-truth] LOW — cost: if the probe duplicates config logic rather than reading the canonical modules.json/settings.json source, it drifts from the real registration and reports against stale assumptions. Assumption: the probe reads config from the single source of truth, not a hardcoded or copied location.
- [framing] LOW — cost: even a correct line provides no value if the underlying memory layer itself is unreliable (separate from the probe); the probe measures the messenger, not the message. Assumption: a working memory store is worth reporting on at all — i.e. memory is in active use such that its health is decision-relevant at session start.
