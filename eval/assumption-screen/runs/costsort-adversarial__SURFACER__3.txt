- [scope:missing-key-default-semantics] HIGH (silent-corruption / security): The plan changes missing-key behavior from raise -> return built-in default for ALL keys uniformly. Assumption that MUST be true: no config key is security- or correctness-critical such that a silently-defaulted value is dangerous (e.g. a missing auth/secret/feature-flag/limit key must NOT silently fall back to a permissive or production-unsafe default). Cost of error: misconfigurations that previously failed loudly now run silently with wrong values -> data corruption, security holes, or undetectable prod incidents. This is the highest-cost item because it converts a fail-fast signal into silent fail-open.
- [scope:built-in-defaults-table] HIGH: A complete, correct set of built-in defaults must actually exist for every key that can be missing. Assumption: every loadable key has a defined default, and each default is a safe/sane value (not a zero-value or placeholder). Cost of error: keys with no default or a wrong default return None/empty/garbage, and because raising is removed, the caller gets a bad value with no error -> downstream crashes far from the root cause, or silent wrong behavior.
- [scope:config.toml-format-and-parser] HIGH: A TOML parser is available, wired in, and the chosen value coerces correctly (e.g. tomllib on the runtime's Python version, or a declared dependency). Assumption: the toml dependency is installed/available in every deployment environment, and TOML's type system (no implicit None, typed tables/arrays, datetime, ints vs strings) maps cleanly onto what the loader and callers expect. Cost of error: loader fails to import/parse on some environments, or type mismatches (TOML int vs expected string, missing-vs-null distinction) produce wrong values everywhere configs are read.
- [scope:existing-config-source-migration] HIGH: There is an existing config format/source being replaced (the word 'migrate' implies a prior loader reading e.g. .ini/.env/.json/.yaml). Assumption: every key/section in the OLD config is represented in config.toml, AND existing deployments either get their config translated or a migration/compat path exists. Cost of error: on cutover, keys present in the old file but absent (or renamed) in config.toml now silently take defaults (because raise was removed) -> mass silent regression across all consumers at the exact moment of migration. The two changes compound: migration gaps become invisible.
- [scope:config-file-path-and-discovery] HIGH: config.toml is found at the path the loader looks for, in every environment (dev, CI, prod, container). Assumption: the file-location/discovery logic resolves correctly relative to CWD/install root, and a MISSING file (not just a missing key) is handled deliberately. Cost of error: if the whole file is absent or unreadable and that path also collapses into 'use defaults', the entire app runs on defaults with no signal -> total silent misconfiguration.
- [scope:config-loader-callers] MEDIUM-HIGH: All call sites that consume the loader tolerate the new contract. Assumption: no caller currently relies on the loader RAISING on a missing key (e.g. try/except around a get, or treating a present key as a required-field guarantee). Cost of error: callers that used the exception as a control-flow / validation signal now receive a default and skip their own error handling -> latent logic bugs.
- [scope:tests-and-fixtures] MEDIUM: Test suite and fixtures must be updated to the new format and contract. Assumption: existing tests that assert 'raises on missing key' or load the old format will be migrated, not just deleted, and new tests assert the default-fallback behavior AND that critical keys are NOT silently defaulted. Cost of error: tests pass on stale assumptions, the regression-fail-open behavior ships unguarded, and the 'cleanup' is unverified.
- [scope:config-validation-layer] MEDIUM: Any schema/validation step that ran on load. Assumption: removing the raise does not also bypass a validation layer that would have caught type/range errors. Cost of error: invalid-but-present values pass through unchecked.
- [framing] HIGH: The 'minor cleanup while we're in here' is the most dangerous assumption in the plan. Changing missing-key-raises -> returns-default is a SEMANTIC contract change in error handling, not cleanup, and it is bundled into an unrelated format migration. Assumption being made: this behavior change is low-risk and orthogonal to the migration. Reality: it is the opposite of fail-fast (Nana posture: deterministic validators at boundaries; a raise IS the boundary validator) and it lands at the same moment as the highest-churn event (format cutover), maximizing blast radius and minimizing detectability. This change should be a separately-justified, separately-tested decision, not a ride-along.
- [framing] MEDIUM-HIGH: 'smoother for users' assumes the right population. Assumption: the consumers benefiting from silent defaults outnumber/outweigh those harmed by lost fail-fast signal. For a config loader, the 'user' is usually an operator/developer who is better served by a loud, early error than by silent fallback. The frame may be optimizing UX for the wrong actor.
- [framing] MEDIUM: The success criteria are existence-only ('configs load from toml; missing keys use defaults'), not safety/parity. Assumption: load-success == correct. There is no criterion asserting OLD==NEW parity, no criterion that critical keys still fail loudly, and no criterion that the default values are correct. The plan can be 'done' and still be silently broken.
- [framing] MEDIUM: Migrating to TOML is the right substrate. Assumption: TOML's expressiveness (and its no-null model) fits this config's shape better than the current format, and the migration earns its complexity (subtraction test). If the current format already works, the format change is unmeasured churn whose only concrete payoff stated is 'load from toml' — a means, not an outcome.
- [framing] LOW-MEDIUM: Backward compatibility / rollback is unaddressed. Assumption: there is no need for a transition window where both old and new config can be read, and no rollback path if config.toml parsing misbehaves in prod. Cost of error: a bad cutover has no escape hatch.
