- [scope:settings.json mcpServers cwd] CRITICAL: The MCP server process must launch with the correct working directory so the SQLite DB lands at the path the agent reads from — cost-of-error: the server starts and tools respond, but writes go to one DB and reads from another, so recall silently returns nothing while every call appears to succeed (this is the documented historical failure: Claude Code ignores settings.json cwd and uses the project dir, putting the DB at <project_root>/.memory/memory.db not ~/.claude/.memory/).
- [scope:memory.db persistence path] CRITICAL: The SQLite store must persist on disk at a stable, agreed path that survives session end and is identical across sessions — cost-of-error: this is the entire success criterion; if the path differs between session 1 and session 2 (CWD-dependent, temp dir, or per-project vs global), the cross-session recall the plan promises is structurally impossible even with everything else working.
- [scope:python -m memory_server launch + module resolution] HIGH: `python -m memory_server` must resolve the module on the PATH/interpreter Claude Code actually spawns, with the package importable (correct venv, dependencies installed) — cost-of-error: server fails to start or import-errors at launch, MCP registration appears present but no memory tools exist; agent silently has no store/search capability.
- [scope:settings.json registration schema] HIGH: The mcpServers entry must be merged idempotently into settings.json in the schema Claude Code expects (command/args/cwd shape) without clobbering existing config — cost-of-error: malformed or overwritten settings.json breaks MCP entirely or corrupts unrelated hook/permission config, regressing the whole harness, not just memory.
- [scope:memory_store / memory_search tool exposure] HIGH: The running server must actually expose memory_store and memory_search over MCP stdio, and the agent client must discover and be permitted to call them in a normal session — cost-of-error: registration succeeds but the named tools aren't surfaced/allowed, so 'confirm the agent can call' fails and there is no recall path.
- [scope:store/search round-trip fidelity] HIGH: A stored decision must be retrievable by a later search — i.e., search recall must surface the prior entry given a reasonable query (FTS/embedding tokenization, dedup, and query sanitization must not drop it) — cost-of-error: data persists but search never returns it (known limitations: char-level sanitizer mangles tokens like C++→C; dedup may suppress; embedding provider absent), so the success test fails despite a correct write.
- [scope:cross-session DB schema/state continuity] HIGH: Session 2 must read the same DB schema and column semantics session 1 wrote (no schema reset, no is_active vs active column mismatch, no per-session reinit) — cost-of-error: prior entries become irrecoverable across the boundary even though they were written (documented: a health probe checked the wrong column and made phases of entries invisible).
- [scope:agent invocation discipline] MEDIUM: The agent must actually call memory_store at decision time in session 1 and memory_search at the right moment in session 2 — cost-of-error: capability is wired but unused (memory is voluntary/nudge-only), so the success criterion never triggers and 'recall across sessions' never happens in practice regardless of infrastructure.
- [scope:verification method] MEDIUM: The confirmation must be a live functional round-trip (write in one real session, read in a genuinely separate next session), not a presence check of the registration — cost-of-error: a registered-but-dormant server passes a config-presence test and ships broken; the plan's own success bar is only met by an end-to-end recall test.

(Prior measurement found harness re-presentation of recoverable decisions adds null value; cross-session decision retention was specifically measured as recoverable from code+tests.)
- [framing] Is an MCP memory server the right substrate at all, versus the always-loaded .claude/rules/ files (working-knowledge/active-knowledge) or the dev-wiki — given documented preference to strengthen always-loaded activation points over adding a separately-wired stateful component that can drift or go dormant.
- [framing] Will the measured/assumed benefit of stored recall replicate in normal use rather than being a setup-time artifact — i.e., across many real sessions does stored memory actually change agent behavior, or does a strong baseline model recover the same decisions unprompted (making the recall path exercised but inert)?
- [framing] Is reliability the real risk rather than functionality — this exact component has a multi-phase history of silent cascade failure (CWD/path/column mismatches that look healthy but lose data); the framing 'enable it and confirm once' under-weights the dominant failure mode, which is silent regression after it appears to work.
