- [framing] The problem is worth solving at all: unspecced implementation work is actually a real, recurring failure mode in consuming projects — if developers rarely skip the spec, a blocking gate adds friction with no benefit (cost-of-error: a hard PreToolUse BLOCK on every edit is the most disruptive possible intervention for a problem that may not exist).
- [scope:PreToolUse-hook-mechanism] The PreToolUse hook must actually fire — it is installed AND registered AND invoked by Claude Code before the matched tool runs; a registered-but-dormant hook passes a file-presence test yet ships completely broken, silently disabling all enforcement (verify by piping a real event and asserting exit 2, not by checking the script exists).
- [scope:exit-code-contract] Claude Code must treat exit 2 from a PreToolUse hook as a hard BLOCK that prevents the tool from running (not merely a warning to stderr, not advisory) — if the exit-2→block semantics are wrong or version-dependent, the hook runs but nothing is ever blocked and the success criterion silently fails.
- [scope:spec-marker] The spec marker the hook tests for must actually exist as a discrete, reliably-detectable artifact with stable semantics — an 'approved spec' must reduce to a checkable file/string the script can grep; if 'approved' is fuzzy or the marker is absent on legitimately-approved specs, the hook either never blocks or blocks valid work.
- [scope:spec-marker-path] The hook must look for the marker at the path where it actually lives in a consuming project — CWD/project-root resolution must be correct (if Claude Code runs the hook from a non-root CWD, a bare-relative marker path 404s and the marker reads as 'absent', BLOCKING all work; this is the exact Phase 79 ${CLAUDE_PROJECT_DIR} class defect).
- [scope:fail-open-vs-fail-closed] The script's error/edge behavior must be deliberate and correct: missing jq, unreadable marker file, or unexpected input must NOT silently exit 2 — a fail-CLOSED bug locks the user out of their own project (self-lockout), while a fail-open bug means enforcement never engages. The plan specifies neither.
- [scope:implementation-work-classifier] The PreToolUse matcher must correctly scope WHICH tools count as 'implementation work' — PreToolUse fires per-tool, but 'implementation work' is not a tool; if the matcher is too broad it blocks reads/planning/spec-writing itself (chicken-and-egg: can't write the spec because editing is blocked), too narrow and real implementation slips through.
- [scope:hook-installer] The installer/registration mechanism that places enforce-spec.sh and writes it into settings.json in a CONSUMING project must exist and run — the success criterion is measured 'in a consuming project,' but the plan describes authoring artifacts in the kit, silently assuming the install path (cp + JSON merge) is wired and idempotent.
- [scope:settings.json] settings.json must accept the registration via a valid, current-schema hook entry (nested {matcher, hooks:[{type:command, command}]} per /doctor) merged idempotently without clobbering existing hooks — a flat or malformed entry triggers /doctor errors and the hook may not load.
- [framing] Hook-based enforcement is the right substrate: hooks can be unwired/disabled, and this project's own history records 3 cascade failures where an uninstalled marker or unwired hook silently disabled all enforcement — a deterministic boundary gate that fails-closed-by-mistake is higher cost-of-error than the unspecced-work it guards against.
- [framing] An opt-in escape hatch is unnecessary: a hard block with no documented override assumes there is never a legitimate reason to edit without an approved spec (hotfix, exploratory spike, security fix) — if such cases exist, an all-or-nothing gate will be circumvented or disabled wholesale, defeating the purpose.
