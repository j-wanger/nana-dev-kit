- [scope:mcp-server-cwd] The MCP memory server's working directory must resolve to the path where the SQLite DB actually lives — cost-of-error: HIGHEST. Prior kit history shows Claude Code IGNORES settings.json `cwd` and uses the project directory, putting the DB at <project_root>/.memory/memory.db, NOT ~/.claude/.memory/. If unverified, store() writes to one path and search() reads another (or a fresh empty DB each session), so cross-session recall silently returns nothing while every call reports success. This is the single defect that makes the plan's success criterion (recall next session) fail invisibly.
- [scope:memory-db-persistence] The SQLite store must persist at a stable, correct path across session boundaries and survive process restart — cost-of-error: HIGHEST. The entire success criterion is cross-session recall; if the DB path is per-CWD, ephemeral (tmp), or re-initialized per launch, decisions written in session 1 are unreachable in session 2. Must verify: the file exists at the assumed path after a store, and the same path is opened on the next session's search. Prior art: 'Phase 19-48 entries irrecoverable' from exactly this class of path mismatch.
- [scope:memory_store-write-semantics] memory_store must actually commit a durable, queryable row (correct table/columns, embedding or word-overlap fallback functioning) — cost-of-error: HIGH. If the schema column the health probe/search expects is wrong (prior evidence: probe checked `is_active` vs actual `active`), or auto-embed silently fails with no fallback, a 'stored' decision is never matched by search even within the same DB. Verify a store→search round-trip returns the row, not just that the call returns 200.
- [scope:memory_search-recall] memory_search must retrieve the just-stored decision via the query the agent would naturally issue — cost-of-error: HIGH. FTS5/vector retrieval can store-but-not-find if the query is sanitized/tokenized differently from index time (known limitation: 'C++' becomes 'C'), or if RRF/threshold tuning drops the match. The plan's success test must use a realistic recall query, not the exact stored string, or it validates nothing about real next-session recall.
- [scope:server-launch-python-m] `python -m memory_server` must launch successfully under the Python interpreter and PYTHONPATH Claude Code actually uses for MCP stdio — cost-of-error: HIGH. If the module isn't importable in that environment (missing venv, package not on path, missing deps), the MCP server fails to start and ALL memory tools are unavailable — but a fail-open harness may surface this only as tools silently absent. install.sh added an import-check after MCP registration precisely because this broke since Phase 4. Verify the import-check passes, not just that settings.json has an entry.
- [scope:settings.json-mcpServers-registration] The mcpServers block must be merged into settings.json idempotently in the schema Claude Code's MCP loader accepts — cost-of-error: HIGH. Hand-editing or a malformed merge can corrupt settings.json (breaking other hooks/MCP) or register a server Claude Code never spawns. The kit's canonical path is scripts/register-settings.py doing an idempotent merge (3 cases: no file / no mcpServers / existing mcpServers); a bare hand-edit risks drift and a registered-but-never-spawned server that passes a presence check but is dead.
- [scope:embedding-provider-deps] If recall relies on vector similarity, the embedding provider (e.g. nomic-embed-text 768d matching the vec0 table) must be present and dimension-matched — cost-of-error: MEDIUM. fastembed + sqlite-vec are benchmark-only and NOT in install.sh, so a plain enable likely runs the word-overlap FTS5 fallback. That's acceptable IF the success test tolerates lexical-only recall; it's a silent quality regression if the plan assumes semantic recall. Confirm which path is live before claiming recall works.
- [framing] The success test 'recorded in one session, recalled in the next' must be executed end-to-end across an actual session boundary (new process, new CWD context), not simulated within one session — cost-of-error: HIGH. Same-session recall passes trivially via in-process state or a warm DB handle and would mask the exact CWD/path persistence bug that has bitten this kit repeatedly. The validation is only meaningful if it crosses a real restart.
- [framing] Storing/recalling decisions must actually be VOLUNTARY-but-used, not just available — cost-of-error: MEDIUM. The kit's own memory-architecture classification rates MCP memory as 'voluntary (nudges only)' — the weakest activation layer, historically subject to cascade failures. Enabling the server does not guarantee the agent reliably calls store at decision time; without a nudge/enforcement path the feature can be wired correctly yet sit dormant. 'Is it firing?' is distinct from 'is it installed?'.
- [framing] Cross-session decision retention via re-presentation must be worth the complexity at all — cost-of-error: MEDIUM. Directly counter to this repo's measured prior: the Phase 77 cross-session-retention headroom screen found residual 0/14 — every tested decision was recoverable from code+tests, so a frontier model gains ~nothing from a harness re-presenting stored decisions. Before investing in MCP memory, confirm the decisions you want recalled are NOT already recoverable from artifacts; otherwise the effect may not replicate and the subtraction test says cut.
- [framing] The chosen substrate (MCP SQLite memory server) is the right approach versus the always-loaded .claude/rules/ layer — cost-of-error: MEDIUM. Kit guidance: 'strengthen existing activation points (.claude/rules/ always loaded), don't add hooks/servers that can be unwired — 3 cascade failures across project history.' A new MCP dependency is a fragile, unwirable layer; an always-loaded rules file or dev-wiki may deliver cross-session recall more robustly for the decisions that matter.
